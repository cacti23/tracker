🔗 Linked List

A learning sheet — there are barely any "algorithms" here. It's pointer hygiene: a sentinel head, and never overwrite a pointer before you've saved what it pointed to.

🧠 1 · How to think (and invent it)

A node is just { val, next }. You can't index it; you can only walk forward and rewire .next. Almost every bug is one of two things: you lost a reference (overwrote a pointer before saving what came next), or you special-cased the head and got it wrong.

Your two superpowers (1) The sentinel / dummy head: a fake node in front of head so "delete/insert at the front" stops being a special case — you always have a prev. (2) Save-before-rewire: before x.next = …, stash const next = x.next, or the tail of the list vanishes. And always: draw the arrows before you type.

Watch it get invented — Reverse a List

Reverse 1 → 2 → 3 in place, O(1) space. The naive cur.next = prev looks right… and instantly orphans the rest of the list.

  1. The trap. If you flip cur.next to point backward before remembering cur.next, you can never reach node 2 or 3 again.
  2. The fix. Carry three pointers: prev (already-reversed part), cur (node being flipped), and a saved next (the untouched rest). Each step: save next → flip → advance both.
  3. Payoff. One pass, no extra memory; prev ends as the new head.

🧩 4 · The four core patterns

Node shape throughout: class ListNode { val: number; next: ListNode | null }. Each pattern: a one-liner, a 🔑 invariant, a template, and a 🎤 interview lens.

4.1 · Reversal — the prev / cur / next dance

“Save next, flip the arrow back, slide both pointers forward.”

🔑 Invariant — why it's safe At every step, prev heads the fully-reversed prefix, cur is the next node to flip, and the saved next still anchors the untouched rest. No node is ever unreachable, so nothing is lost.
function reverseList(head: ListNode | null): ListNode | null {
  let prev: ListNode | null = null, cur = head;
  while (cur) {
    const next = cur.next;   // SAVE before rewiring
    cur.next = prev;         // flip the arrow backward
    prev = cur; cur = next;  // advance the window
  }
  return prev;               // new head
}
Builds on itself Reverse between [m, n]: walk to node m−1 (use a dummy), reverse exactly n−m+1 nodes, reconnect the three boundaries. Reverse in k-groups: check k nodes exist, reverse them, recurse/iterate on the rest, stitch.
🎤 Interview lens Probed: save-next-first, O(1) space, then the recursive version (and its O(n) stack). · Escalation: reverse → reverse sublist [m,n] → reverse in k-groups (the boundary reconnection is the real test).

4.2 · Fast & slow runners

“Two speeds turn ‘where's the middle / is there a loop?’ into one pass.”

Setup: slow += 1, fast += 2. This is the linked-list face of the fast & slow two-pointer — the proofs live there; here are the four staples.

🔑 Invariant — why it's safe When fast has taken 2t steps, slow has taken t — so slow is always at the halfway mark of where fast reached. That single fact gives you the middle, and (with a cycle) forces a meeting.
// Middle node (for even length, returns the second middle)
function middleNode(head: ListNode | null): ListNode | null {
  let slow = head, fast = head;
  while (fast && fast.next) { slow = slow!.next; fast = fast.next.next; }
  return slow;
}

// Palindrome list: find middle → reverse 2nd half → compare
function isPalindrome(head: ListNode | null): boolean {
  let slow = head, fast = head;
  while (fast && fast.next) { slow = slow!.next; fast = fast.next.next; }
  let prev: ListNode | null = null;            // reverse from slow
  while (slow) { const n = slow.next; slow.next = prev; prev = slow; slow = n; }
  let a = head, b = prev;                       // compare halves
  while (b) { if (a!.val !== b.val) return false; a = a!.next; b = b.next; }
  return true;
}
🎤 Interview lens Probed: the while (fast && fast.next) guard, and why slow lands on the middle. · Escalation: middle → detect cycle → cycle start (the reset trick) → palindrome (restore the list afterward if asked).

4.3 · Dummy head & splicing

“Put a fake node in front so the head is never a special case.”

Setup: create dummy with dummy.next = head, keep a moving tail/prev, and return dummy.next. Deletions and merges that would touch the head now Just Work.

🔑 Invariant — why it's safe dummy.next is always the true current head, and tail is the last node of the result built so far. Because dummy never moves, the answer is one dereference away no matter how the front changes.
// Merge two sorted lists
function mergeTwoLists(a: ListNode | null, b: ListNode | null): ListNode | null {
  const dummy = new ListNode(0); let tail = dummy;
  while (a && b) {
    if (a.val <= b.val) { tail.next = a; a = a.next; }
    else                { tail.next = b; b = b.next; }
    tail = tail.next;
  }
  tail.next = a ?? b;            // attach the remaining run
  return dummy.next;
}

// Remove n-th node from the end — one pass, dummy avoids the head edge-case
function removeNthFromEnd(head: ListNode | null, n: number): ListNode | null {
  const dummy = new ListNode(0, head); let fast = dummy, slow = dummy;
  for (let i = 0; i < n; i++) fast = fast.next!;   // open a gap of n
  while (fast.next) { fast = fast.next; slow = slow.next!; }
  slow.next = slow.next!.next;                      // slow sits just before the target
  return dummy.next;
}
🎤 Interview lens Probed: exactly why the dummy removes the head special-case; the gap of n in remove-n-th. · Escalation: merge → "Merge k Sorted Lists" (→ a heap; see the Heap sheet) → partition list → add two numbers (carry).

4.4 · Compose the primitives

“Hard list problems = find-middle + reverse + merge, glued together.”

Setup: the toughest problems decompose into the primitives above. The discipline that makes them work: null-terminate between stages so you don't accidentally weld a cycle.

🔑 Invariant — why it's safe Each stage leaves a clean, null-terminated list for the next. Cut the first half off (slow.next = null) before reversing the second, so the interleave step can't loop forever on a dangling link.
// Reorder List:  1→2→3→4→5  becomes  1→5→2→4→3
function reorderList(head: ListNode | null): void {
  if (!head || !head.next) return;
  let slow = head, fast = head;                            // 1) middle
  while (fast.next && fast.next.next) { slow = slow.next!; fast = fast.next.next; }
  let second: ListNode | null = slow.next; slow.next = null;   // cut!
  let prev: ListNode | null = null;                        // 2) reverse 2nd half
  while (second) { const n = second.next; second.next = prev; prev = second; second = n; }
  let first: ListNode | null = head; second = prev;        // 3) interleave
  while (second) {
    const f = first!.next, s = second.next;
    first!.next = second; second.next = f;
    first = f; second = s;
  }
}

// Swap nodes in pairs — dummy + careful rewire
function swapPairs(head: ListNode | null): ListNode | null {
  const dummy = new ListNode(0, head); let prev = dummy;
  while (prev.next && prev.next.next) {
    const a = prev.next, b = a.next!;
    a.next = b.next; b.next = a; prev.next = b;   // prev → b → a → …
    prev = a;
  }
  return dummy.next;
}
🎤 Interview lens Probed: decompose into named primitives, and the null-terminate step that prevents an accidental cycle. · Escalation: reorder → "Rotate List by k" (close into a ring, walk to the new tail, break) → swap pairs → swap k-th node from both ends.

⏱️ 5 · Complexity

OperationTimeSpaceNote
Reverse / traverse / fast-slow / spliceO(n)O(1)iterative; recursion adds O(n) stack
Access the i-th nodeO(n)O(1)no random access — this is the whole trade-off vs an array
Merge k lists (with a heap)O(n log k)O(k)heap of the k current heads
The one cost to remember Everything is O(1) space and O(n) time as long as you never re-walk from head inside a loop. The instant you do (e.g. "find length, then for each node re-scan"), you've slipped to O(n²). Keep running pointers.

⚠️ 6 · Pitfalls — and the test that catches each

BugThe input that exposes it
Overwriting .next before saving it — orphaning the tail.Any reverse of length ≥ 2 without a temp → you lose everything after node 1.
No dummy head → mishandling deletion of the first node.Remove the head, or a list that becomes empty → null-pointer or wrong head returned.
Fast/slow without the fast && fast.next guard.Empty list [] or single node [1] → crash on fast.next.next.
Forgetting to null-terminate after splitting.Reorder / palindrome on even length → the interleave/compare loops forever (a welded cycle).
Off-by-one in remove-n-th (gap of n vs n+1).n == length (remove the head) → without the dummy + gap-of-n, you skip the wrong node.
Comparing node identity when you meant value (or vice-versa).Cycle detection vs duplicate values → equal values are not the same node.
