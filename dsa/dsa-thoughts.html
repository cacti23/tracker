1 · 🧱 Grid Traversal — Blocked Start/Destination

Before starting, check if start OR destination is blocked (-1, thorn, obstacle). Handle immediately.

2 · 🌳 Grid Brute Force — TC = branch^depth

  • 4 directions → branch≈4, depth≈M×N → O(4^(M×N))
  • Right/down only → branch=2, depth=M+N → O(2^(M+N))

Loose bounds — actual cost depends on visited-tracking and work per call.

3 · 🧭 Standard Direction Array

Top → Right → Down → Left

[-1,  0]
[ 0,  1]
[ 1,  0]
[ 0, -1]

4 · 🔁 Kahn's Algorithm — Cycle Detection (Directed)

Peel nodes with indegree=0 repeatedly. Cycle nodes NEVER hit 0.

📌 One-line processedNodes < totalNodes → cycle exists.

5 · ✈️ Hierholzer's Algorithm

For Eulerian paths — visit every EDGE once, not every node. Push node to result on the way OUT (post-order) → reverse at the end.

6 · 🔢 Sieve of Eratosthenes

📌 One-line TC = O(n log log n) — sum of n/p over all primes p ≤ n.

7 · 🎯 Dijkstra — Initialization

Weighted graph, non-negative weights → think Dijkstra.

dist[node] = Infinity
dist[source] = 0
🔑 Mental swap BFS → visited[]. Dijkstra → dist[] = ∞.

8 · 📐 Grid as Graph — V+E Complexity

V = M×N
E <= 4×M×N
V+E = MN+4MN = 5MN = O(MN)
🔑 Grid BFS/DFS → O(MN), the constant 4 drops.

9 · 🌲 Serialize/Deserialize Tree → think PREORDER

  • Binary Tree (297): preorder + null markers
  • BST (449): preorder alone suffices — BST bounds preserve structure

10 · 🔍 BST → think INORDER first

Inorder on a BST = sorted order. Use for:

  • Kth smallest/largest
  • Validate BST
  • Predecessor/successor
  • Recover BST
⚠️ Not universal — sometimes bounds/preorder/postorder fit better.

11 · 🔦 BFS vs Backtracking (DFS)

🎯 Do I need the SEQUENCE of cells I took, or only the answer at the end (reachable / count / min steps)?

I needApproachExamples
✅ Only reachability, a count or min stepsBFS (or plain DFS), mark visited foreverRotting Oranges, Number of Islands
🚨 The sequence itself, or the route affects the ruleBacktracking = DFS + undo: mark → explore → restoreMax Gold, Unique Paths III, Word Search
📌 Backtracking IS DFS with undo. BFS keeps many partial paths in the queue at once, so it can't undo one path — when the sequence matters, go DFS + restore.

12 · 🌳 Tree Traversal as Undirected Graph — Parent Map

Trees only give CHILD pointers (left/right) — no way UP.

🎯 Don't build a full adjacency-list graph — just add the ONE missing piece: parent.

📐 One DFS pass, passing (node, parent), building parentMap.set(node, parent).

🔑 Then treat the tree as undirected: left, right, AND parentMap.get(node) = 3 directions.

Used for: All Nodes Distance K in Binary Tree (863) — any problem needing "go up" in a tree.

13 · 🎯 Dijkstra — Why dist[] Is Always Needed

🎯 Only trust a path if it's the CHEAPEST way found SO FAR to a node.

dist[node] = best cost discovered so far.

🚨 A node CAN be pushed to the queue multiple times (once per improving path). dist[] decides: is THIS entry still the best, or has something better already replaced it?
if (currTime > dist[row][col]) continue;  // stale — a better path already won
📌 dist[] guarantees you only ever ACT using a node's LOWEST known cost, never a stale worse one.

14 · ⏱️ Dijkstra Complexity — How Many Times Can an Edge Relax? (NOT from V+E)

🎯 Relax = an edge finds a smaller distance to a node → update dist[] and push.

Q1. How many times can an edge relax? Once each — an edge is only looked at when its source node is popped for real (not a stale entry). So at most E relaxations → at most E pushes.

Q2. Cost of one push/pop? The heap holds up to E entries → log E.

📐 Total: E × log E = O(E log E) — V never appears.

📌 Complexity = (how many times can an edge relax) × (cost per relax). Dijkstra: E × log E. Same question for Bellman-Ford: every edge can relax up to V−1 times → O(V·E).

15 · 🔁 When Visited Is REQUIRED vs Optional

🎯 Ask one question: can I walk back to where I came from?

What am I walking?                        visited?
Binary tree (child pointers only)      →  NO        (no way back up)
Tree as an edge list (undirected)      →  skip PARENT (or visited)
Undirected graph / grid                →  YES       (edge u–v goes both ways = a tiny cycle)
Directed graph WITH a cycle            →  YES
DAG (no cycle)                         →  optional  (speed only)
🚨 "No cycle in the problem" doesn't save an undirected graph — every undirected edge is already a 2-step cycle (u→v→u).
📌 Can walk back → visited required. Can't → optional. One catch: if the same node must appear in several valid paths (Word Ladder II reconstruction), visited can wrongly block the second one.

16 · ✈️ Hierholzer's DFS — TC = O(E), NOT V+E

🎯 Every edge is CONSUMED exactly once (nei.pop() permanently removes it).

🚨 A NODE can be visited MULTIPLE times (once per outgoing edge it has) — so "V node-visits" isn't a meaningful separate count here.
🔑 Total work = total edges popped = O(E) alone. No +V term needed — E already captures ALL the work.
📌 Whenever a DFS CONSUMES each edge exactly once (Hierholzer's / Eulerian path problems) → TC = O(E), not V+E.

17 · ⚖️ V+E Is a Shortcut — Only Safe When Work Is O(1)

🎯 V+E secretly means V×(work per node) + E×(work per edge).

✅ When work per node/edge is O(1) (a comparison, a fixed neighbor check) → safely write just V+E.

🚨 When work per node/edge is MORE than O(1) (building a string, computing a hash) → must EXPLICITLY multiply:
Total = (V × work per node) + (E × work per edge)

📐 Example — removeInvalidParentheses: V=2^n states, E=2^n·L edges (L removal-choices per state), work per edge = O(L) (string slice).

Total = 2^n×L (work per node, building L edges) + (2^n·L)×L (work per edge)
      = O(2^n · L²)
📌 Don't default to "V+E" blindly — check the cost of ONE unit of work first. If it's O(1), V+E is fine as-is. If it's O(k), multiply that k into both terms explicitly.

18 · 🎯 Sentinel-Seeding: When It's Safe vs When It's Not

🎯 The REAL question: does my function have an EXPLICIT base case, or is the "seed value" secretly ACTING as the base case?

✅ Explicit base case exists (if(...) return 0; / a clean, dedicated return) → sentinel-seeding is SAFE, don't overthink it. The base case ALWAYS overrides the sentinel with a real answer.

function dfs(row, col) {
    if (invalid) return 0;          // explicit base case, resolves cleanly
    ...
    let maxGold = 0;                 // sentinel is fine, loop always gets overridden
    for (...) maxGold = Math.max(maxGold, dfs(...));
    return currGold + maxGold;       // add currGold ONCE, here
}
🚨 NO explicit base case (a "dead end" is just "the loop found nothing," no dedicated return) → the SEED value ITSELF is the base case's answer. It MUST equal the correct "nothing more to add" result — NOT a generic sentinel.
function dfs(row, col) {
    // no explicit base case — dead end = loop simply doesn't run
    let maxGold = currGold;          // seed = the correct dead-end answer itself
    for (...) maxGold = Math.max(maxGold, currGold + dfs(...));
    return maxGold;
}
📌 Explicit base case → sentinel-seeding is safe, base case always resolves it. NO explicit base case → the seed IS the base case, so it must already equal the correct answer for "nothing more happens here" — not a placeholder.

19 · 🚦 Plain BFS vs Dijkstra — Which One to Use

✅ Edges all cost 1 → Plain BFS.

🚨 Edges have DIFFERENT weights → Dijkstra.

Why: plain BFS assumes "visited first = reached via shortest path." That's ONLY true when every step costs the same — nothing can skip ahead of a shorter path.

📐 Concrete break: start→A costs 10 directly. start→B→A costs 1+1=2. If A gets visited FIRST via the expensive 10 edge, it's locked in with the WRONG distance — the cheaper path via B gets blocked.

📌 Weight-1 edges → BFS is safe. Any varying weights → Dijkstra (priority queue + dist[]), since "visited first" no longer means "shortest."

20 · 🎯 Binary Search — Master Summary

🔍 Normal (find exact element)

🔑 low/high are ARRAY INDICES — you navigate by index, but compare the ELEMENT'S VALUE at that position.
low = 0, high = n-1
while (low <= high) {
    mid = (low+high) >> 1
    if (arr[mid] === target) return mid
    else if (arr[mid] < target) low = mid + 1
    else high = mid - 1
}
return -1

📐 Boundary search (find a threshold, not an exact element)

🎯 THE ONE THING TO THINK ABOUT: does the ANSWER have to exist WITHIN the range, or could it legitimately be "one past the end"?

  • Searching a VALUE SPACE (weights, thresholds) → high = one past the max real value
  • Searching ARRAY INDICES (like LIS's tails) → high = array.length (one past the last valid index) — "insert past everything" IS a real, valid answer
🔑 Same rule either way — don't treat arrays differently just because they're arrays. Normal search uses n-1 because the answer MUST exist inside; boundary search uses n because it might not.

Style A, searching LEFT (shrink toward smaller):

low = 0, high = n
while (low < high) {
    mid = (low+high) >> 1        // round DOWN
    if (condition(mid)) high = mid
    else low = mid + 1
}
return low   // low === high === the answer

Style A, searching RIGHT (grow toward bigger):

low = 0, high = n
while (low < high) {
    mid = (low+high+1) >> 1      // round UP — REQUIRED
    if (condition(mid)) low = mid
    else high = mid - 1
}
return low   // low === high === the answer

Style A — LIS-specific (lower bound on a REAL ARRAY, e.g. tails in LIS / Russian Doll Envelopes):

lo = 0, hi = arr.length
while (lo < hi) {
    mid = (lo+hi) >> 1
    if (arr[mid] >= target) hi = mid
    else lo = mid + 1
}
// lo IS the answer — insert/replace at lo

📐 Concrete worked example — Russian Doll Envelopes (354), sort by width ASC / height DESC on ties, then LIS on heights:

function maxEnvelopes(env: number[][]): number {
    env.sort((a, b) => {
        if (a[0] === b[0]) return b[1] - a[1];
        return a[0] - b[0];
    });

    const hei = env.map(a => a[1]);
    const tails: number[] = [];

    for (const h of hei) {
        let lo = 0, hi = tails.length;
        while (lo < hi) {
            const mid = (lo + hi) >> 1;
            if (tails[mid] >= h) hi = mid;
            else lo = mid + 1;
        }
        if (lo === tails.length) tails.push(h);
        else tails[lo] = h;
    }

    return tails.length;
}

Style B (kept for reference — see recommendation below):

low = 0, high = n, ans = -1
while (low <= high) {
    mid = (low+high) >> 1
    if (condition(mid)) { ans = mid; high = mid - 1 }  // searching LEFT
    else low = mid + 1
}
return ans
🎯 Honest recommendation Default to Style A for ALL boundary search, always. It's strictly less code (no extra ans variable), low/high converge to the answer directly, and it works identically for value-space AND array-index searches. Style B's only "advantage" (matching low<=high's shape from normal search) doesn't actually save complexity once you know Style A's high=n rule — it just adds bookkeeping. Style B is documented here for reference/recognition (some solutions online use it), but there's no real reason to reach for it over Style A.

🗺️ Quick decision

SituationApproach
Exact value exists in array?Normal binary search (low/high = indices, high=n-1)
Threshold/optimal value?Boundary search — default Style A (high=n, whether values or array indices)
  Searching LEFT (shrink)?high=mid, round DOWN — always safe
  Searching RIGHT (grow)?low=mid, round UP — REQUIRED

21 · 🔄 Cycle Detection — All Methods, At a Glance

🔗 UNDIRECTED — 3 ways

1. DFS + parent-skip:

dfs(node, parent):
  visited[node] = true
  for nei in graph[node]:
    if nei === parent: skip
    if visited[nei]: CYCLE
    dfs(nei, node)

2. BFS + parent-skip: same idea, queue holds (node, parent) pairs instead of recursion.

3. Union-Find:

for each edge (u,v):
  if find(u) === find(v): CYCLE
  else union(u,v)

➡️ DIRECTED — 2 ways (Union-Find does NOT apply — no sense of direction)

1. DFS with 0/1/2 marking:

state: 0=unvisited, 1=exploring, 2=done
dfs(node):
  state[node] = 1
  for nei in graph[node]:
    if state[nei]===1: CYCLE (back edge to node still exploring)
    if state[nei]===0: dfs(nei)
  state[node] = 2

2. Kahn's (BFS topological sort):

queue = all nodes with indegree 0
process queue, decrementing neighbors' indegree, adding new indegree-0 nodes
if processedCount !== n: CYCLE (leftover nodes stuck in a cycle)
📌 Undirected → DFS/BFS parent-skip or Union-Find (3 valid ways). Directed → 0/1/2 DFS or Kahn's ONLY — Union-Find can't tell direction apart, so it can't detect directed cycles.

22 · ⏳ 2577 vs 3341/3342 — Can You Wait, or Must You Move?

🎯 All THREE use Dijkstra. The ONE difference: can you WAIT in place?

🚨 2577 (Minimum Time to Visit a Cell in a Grid): NO waiting. Forced to move every step. Arriving too early → must BOUNCE (move away, come back) to kill time → needs PARITY math:
if (neiTime <= currTime+1) nextTime = currTime+1
else if ((neiTime-currTime)%2===0) nextTime = neiTime+1
else nextTime = neiTime

⚠️ Special case: (0,0) has NO parent to bounce with. If BOTH its neighbors need >1 to enter, you're stuck immediately:

if (grid[0][1]>1 && grid[1][0]>1) return -1

✅ 3341/3342 (Reach Last Room I/II): FREE waiting. Just sit and wait, then move:

nextTime = max(currTime, moveTime[nr][nc]) + moveCost
🔑 3341 vs 3342 only the move cost differs: 3341 = fixed +1. 3342 = alternates +1/+2 based on (row+col)%2.
📌 Can't wait → bounce + parity math (2577, plus the (0,0)-no-parent edge case). Can wait → simple max()+cost (3341/3342).

23 · 🚨 JS Never Throws on Out-of-Bounds Array Access

🎯 arr[100] (too big) or arr[-1] (negative) → both silently return undefined. NO crash, NO error.

🚨 Unlike Java/C++/Python — those THROW immediately, making the bug OBVIOUS right away.
🔑 Why this is dangerous undefined silently flows into math. Math.min(5, undefined) = NaN. Once NaN appears, it POISONS every calculation built on top of it — but nothing crashes, so the bug hides until the FINAL wrong answer shows up.

📐 Where I hit this: Stone Game DP — dp[i+1][j-1] when j=0 reads dp[1][-1] → undefined → Math.min(0, undefined) = NaN → cascaded corruption through the whole table.

✅ The fix: ?? 0 (or another sensible default) right at the access point:

dp[i+1][j-1] ?? 0   // undefined → 0, before it reaches Math.min/arithmetic
📌 JS out-of-bounds = silent undefined, not a crash. Anywhere an index MIGHT go negative or past the end, guard with ?? default right at the read, or the bug hides until a wrong final answer.

24 · 🎯 Binary Search + BFS vs Binary Search + Dijkstra

🎯 "Can I reach X using only edges ≤ mid?" → BFS. "What's the CHEAPEST path?" → Dijkstra.

🔑 When binary search picks mid (max allowed weight) and FILTERS the graph to weight ≤ mid, the weight-reasoning is ALREADY done externally — the inner check just needs YES/NO connectivity.

📐 Example (LeetCode 3419): minimize the max edge weight so every node reaches node 0. check(mid): filter edges to ≤ mid, then plain BFS — "does everyone reach node 0?" No distances needed, just reachability.

📌 Dijkstra finds the CHEAPEST path. BFS finds IF a path exists at all. Binary-search-on-threshold problems often only need the SECOND question — since binary search already handled "which weights count" outside the check.

25 · 🎯 Dijkstra vs Bellman-Ford — When to Reach for Which

✅ Dijkstra: only works with NON-NEGATIVE weights. Greedy — assumes "once finalized, always correct."

🚨 Negative weights present → Bellman-Ford, not Dijkstra. Dijkstra's greedy assumption BREAKS with negatives (a later negative edge could invalidate an "already finalized" distance).
🔑 Bellman-Ford bonus detects negative cycles too — run one EXTRA round past V-1; if anything STILL improves, a negative cycle exists.

🎯 Second trigger for Bellman-Ford (no negative weights needed): "at most K stops/edges" constraints. K stops maps directly to K+1 bounded relaxation rounds — e.g., Cheapest Flights Within K Stops (787). Dijkstra can't express this cap without extending its state; Bellman-Ford's round-by-round structure handles it naturally.

⚠️ Not "Bellman-Ford needs directed graphs" — the real rule: UNDIRECTED + NEGATIVE weight = automatic negative cycle. A single undirected negative edge (u,v,-w) lets you bounce u→v→u forever, decreasing cost each time — that alone IS a negative cycle.

✅ Undirected + NON-NEGATIVE weights → safe to convert to directed (add both u→v and v→u, same weight) and run Bellman-Ford normally — same trick as building an adjacency list for BFS/DFS.

26 · 🌊 Floyd-Warshall — General Application

🎯 Shortest distance between EVERY PAIR of nodes, all at once — not just from one source.

dist[i][i] = 0
dist[u][v] = w for every direct edge (both directions if undirected)

for k in 0..n:        // MUST be outermost — try every "middle stop"
  for i in 0..n:
    for j in 0..n:
      if dist[i][k]+dist[k][j] < dist[i][j]:
        dist[i][j] = dist[i][k]+dist[k][j]

📐 Undirected graph: just set dist[u][v] AND dist[v][u] during init — rest of the algorithm is identical.

⚠️ Math.min during INIT (not the main loop) — apply it whenever the input CAN have multiple edges between the same pair:
dist[u][v] = Math.min(dist[u][v], w)

Safe to ALWAYS include (never wrong) — only STRICTLY required if duplicates are possible. The main triple-loop relaxation never needs this — its own if already keeps the smaller value.

📌 k outermost, always. Undirected = set both directions at init. Math.min at init = protect against duplicate edges — harmless habit, required only if duplicates can exist.

27 · 🎯 Skip/Take vs "Committed Rule" DP — When Skip/Take Breaks

🎯 Skip/Take works when "take or skip" depends on ONE thing: comparing to the LAST picked element.

✅ LIS: "is nums[i] > nums[prev]?" — one comparison, one reference point. Skip/Take works fine.

🚨 Some problems need a rule the CHAIN ALREADY COMMITTED TO — not just the last value:

📐 1027 Longest Arithmetic Subsequence: "does nums[i] continue the SAME DIFFERENCE this chain already has?" — but a chain only HAS a difference once it's got 2+ elements. Skip/Take (state = just prev) can't express this.

🧠 Simple test "To decide take-or-skip at i, do I need just the LAST element, or a RULE the chain already locked in?"
  • Just last element → 🟢 Skip/Take, state = (i, prev)
  • A committed rule (difference, ratio, count) → 🔴 state = (i, thatRule), found via PAIRWISE scan, not skip/take

📌 Problems in this "committed rule" family:

  • 1027 Longest Arithmetic Subsequence — rule = the common difference
  • 673 Number of LIS — rule = "how many ways," tracked alongside length
  • 368 Largest Divisible Subset — needs the actual subset, not just length

🟢 LIS pseudocode (skip/take works — state = just prev):

dfs(i, prevIdx):
  if i === n: return 0
  skip = dfs(i+1, prevIdx)
  take = 0
  if prevIdx === -1 or nums[i] > nums[prevIdx]:
    take = 1 + dfs(i+1, i)
  return max(skip, take)

🔴 1027 Longest Arithmetic Subsequence — recursive framing (state = committed rule, "ending at i"):

// dfs(i, diff) -> longest arithmetic subsequence ENDING AT index i, using common difference diff
memo = map, keyed by (i, diff)

dfs(i, diff):
  if memo has (i, diff): return memo[(i, diff)]
  best = 1   // just this element alone, base length
  for j in 0..i:
    if nums[i] - nums[j] === diff:
      best = max(best, 1 + dfs(j, diff))
  memo[(i, diff)] = best
  return best

answer = max over all i, all diff = nums[i]-nums[j] for j<i, of dfs(i, diff)
🔑 "Ending at i" is the STANDARD framing for this whole family — anchor the state at the LAST index, then ask "for every earlier j, if I extend THAT chain (ending at j, same diff) by adding nums[i], what do I get?" State = (i, diff), not (i, prevIndex) — the DIFFERENCE itself is what got "committed" and must be carried forward.
📌 If the extension rule only needs the LAST value, it's skip/take. If it needs a relationship the chain already locked in, the state must CARRY that relationship — found by scanning PAIRS, not by skip/take.

28 · 🗡️ Dungeon Game — Work Backward, Clamp to 1

🎯 The question at EVERY cell: "how much HP do I need WALKING IN, so that after this cell's effect, I still have enough for the REST of the trip?"

🔑 Work BACKWARD from the destination — a cell's answer depends on EVERY cell AFTER it, so you must know those first.

Base case (destination): need 1 HP left after its effect.

Math.max(1, 1 - dungeon[dest])

Every other cell: pick the CHEAPER of the two paths ahead, then ask what's needed HERE.

neededAhead = Math.min(right, down)
thisCell = Math.max(1, neededAhead - dungeon[cell])

📐 Why neededAhead - dungeon[cell] works for BOTH damage and healing, same formula:

Damage (dungeon=-2): neededAhead - (-2) = neededAhead + 2   // need MORE, correct
Heal (dungeon=+8):   neededAhead - 8                          // need LESS, correct

Subtracting a negative flips to addition automatically — no separate rule needed for damage vs healing.

🚨 Math.max(1, ...) is a hard safety clamp: you can NEVER be alive with 0 or negative HP, even if the math suggests a heal covers it. Always floor at 1.
📌 Walk backward from the end, take the cheaper future path, ask what HP survives THIS cell's effect and still meets that need — always clamped to a minimum of 1, since zero or negative HP is never survivable.

29 · 🕸️ Minimum Spanning Tree — Master Kruskal's, Skip Prim's

🎯 The question: connect ALL nodes together (directly or through others) using MINIMUM TOTAL edge cost. NOT "shortest path between two specific nodes" — that's Dijkstra's job, a DIFFERENT question entirely.

🚨 Why Dijkstra doesn't fit Dijkstra tracks "total DISTANCE from a source" (accumulated along a path). MST doesn't care about distance FROM anywhere — it just wants the CHEAPEST network connecting everyone.

Problems: LC 1584 Min Cost to Connect All Points, LC 1135 Connecting Cities With Minimum Cost, general MST questions.

🔑 Kruskal's and Prim's both compute the IDENTICAL MST — just two different strategies for the same answer. Kruskal's is the ONE to master deeply: it reuses Union-Find (already practiced extensively — cycle detection, removeStones, magnificentSets), and "sort edges, greedily add cheapest ones that don't form a cycle" is simpler to explain out loud than Prim's tree-growing approach. Learning Prim's separately isn't needed — recognizing it exists (in case an interviewer asks to compare) is enough.
// general MST: n nodes, edges = [u, v, weight]
function minCostToConnectAllNodes(n: number, edges: number[][]): number {
    const parent = Array.from({ length: n }, (_, i) => i);
    const rank = Array(n).fill(0);

    function find(x: number): number {
        let root = x;
        while (parent[root] !== root) root = parent[root];
        while (parent[x] !== root) {
            const next = parent[x];
            parent[x] = root;
            x = next;
        }
        return root;
    }

    function union(x: number, y: number): boolean {
        const px = find(x), py = find(y);
        if (px === py) return false;
        if (rank[px] < rank[py]) parent[px] = py;
        else if (rank[px] > rank[py]) parent[py] = px;
        else { parent[px] = py; rank[py]++; }
        return true;
    }

    edges.sort((a, b) => a[2] - b[2]); // sort by weight ascending

    let totalCost = 0, edgesUsed = 0;

    for (const [u, v, weight] of edges) {
        if (union(u, v)) {
            totalCost += weight;
            edgesUsed++;
            if (edgesUsed === n - 1) break; // tree complete
        }
    }

    return edgesUsed === n - 1 ? totalCost : -1; // -1 if graph can't be fully connected
}
🔑 Why Dijkstra doesn't fit here either: Kruskal's isn't tracking distance from anywhere — it's greedily picking GLOBALLY cheap edges while using Union-Find to AVOID cycles, a totally different mechanism from path-distance tracking.
📌 MST (Kruskal's) answers "cheapest way to connect EVERYONE." Dijkstra answers "cheapest way from ONE source to ONE target." Different questions — don't reach for Dijkstra when the problem is really asking for a spanning tree.

30 · 🎲 Stone Game Family — Each Variant Has Its OWN Shape, Don't Force-Fit

🚨 Don't carry one Stone Game's shape over to another by default — the move rule decides the recursion shape.

🅰️ Stone Game I — front/back pick, NO for-loop, Math.min-the-opponent

Every move removes exactly ONE pile from either END (i or j) → state stays a clean interval [i,j]. Two explicit choices only — no loop needed. Opponent (next player) wants to MINIMIZE what's left for you:

function dfs(i: number, j: number): number {
    // base case
    if(i > j) return 0;

    const pickStart = piles[i] + Math.min(dfs(i + 2, j), dfs(i + 1, j - 1));
    const pickEnd = piles[j] + Math.min(dfs(i, j - 2), dfs(i + 1, j - 1));

    return Math.max(pickStart, pickEnd);
}

🅱️ Stone Game II — variable move size, for-loop + suffix sum

Move size X isn't fixed (1..2M) → single advancing pointer i, no "other end." For-loop tries every X, subtracts the opponent's best from here, takes the max:

function dfs(idx: number, m: number): number {
    // base case
    if(idx >= n) return 0;
    if(idx + 2 * m >= n) return suffix[idx]; // must be suffix[idx], NOT suffix[0] — remaining sum, not total sum

    let best = Number.MIN_SAFE_INTEGER;
    for(let x = 1; x <= 2 * m; x++) {
        const taken = suffix[idx] - suffix[idx + x];
        const oppoTake = dfs(idx + x, Math.max(m, x));
        best = Math.max(best, taken - oppoTake);
    }

    return best;
}

🅲 Stone Game VII — front/back pick like SG1, but needs PREFIX SUM for scoring

Like SG1, picks from either end — but the SCORE for a move isn't piles[i]/piles[j] directly, it's the SUM of whatever stones remain after removing that pile. Needs a prefix-sum array for O(1) range-sum lookup. Shape follows SG1 (2 explicit choices, no loop) since it's still a fixed-one-pile-per-move front/back game:

function dfs(i: number, j: number): number {
    // base case
    if(i >= j) return 0;

    const pickFront = (prefix[j + 1] - prefix[i + 1]) - dfs(i + 1, j);
    const pickBack = (prefix[j] - prefix[i]) - dfs(i, j - 1);

    return Math.max(pickFront, pickBack);
}
🎯 Why SG1 alone doesn't use prefix/suffix prefix/suffix exist to sum a RANGE of elements in O(1). SG1's move value is always ONE single pile (piles[i]) — no range, nothing to sum, so there's nothing for prefix/suffix to speed up. SG2 sums a variable-size CHUNK (a range). SG7 sums the REMAINING stretch after a pick (also a range). Rule: reach for prefix/suffix only when a move's value spans more than one element — not just because it's "a Stone Game."
📌 The MOVE RULE decides the shape — copy the move rule, not the code.

31 · 🗺️ Prefix vs Suffix — Where the "Extra" Sentinel Index Sits

index:      0    1    2    3    4    5
piles:    [ 2 ][ 7 ][ 9 ][ 4 ][ 4 ]

suffix:   [26 ][24 ][17 ][ 8 ][ 4 ][ 0 ]
                                    ↑ sentinel (nothing after index 4)

prefix:   [ 0 ][ 2 ][ 9 ][18 ][22 ][26 ]
            ↑ sentinel (nothing before index 0)

🎯 Suffix sentinel sits at the END. Prefix sentinel sits at the START. Both mean the same thing: "empty range → 0."

📌 suffix[i] INCLUDES piles[i], sentinel 0 at the tail. prefix[i] EXCLUDES piles[i], sentinel 0 at the head. Same size (n+1), opposite ends.

32 · 🌲 Unmemoized Recursion TC — 3-Question Framework

🎯 Ask these in order. Stop at the first one that fits.

Q1 — Constant branching? (same # choices every call)

→ branches^depth. (take/skip → 2ⁿ)

Q2 — Variable branching, but is there a FIXED set of positions each getting an independent yes/no?

→ 2^(that count).

Stone Game II: n-1 gaps → cut or not → 2^(n-1)
LC 131 Palindrome Partitioning: n-1 gaps → cut or not → 2^(n-1)

Q3 — Branching is a SPLIT POINT choice (pick k, recurse both sides)?

→ Catalan-shaped: dfs(i,j) = Σ dfs(i,k) ⊗ dfs(k,j)

function dfs(i: number, j: number): number {
    if (i >= j) return 1;
    let total = 0;
    for (let k = i; k < j; k++) {
        total += dfs(i, k) * dfs(k + 1, j);   // k = split point
    }
    return total;
}

k = root (96 Unique BST), last-op (241), last-burst (312 Burst Balloons), matrix-split (Matrix Chain Mult — the textbook Catalan recurrence itself).

None of the above fits?

→ Just say "exponential, no clean polynomial form" — honest, accepted answer.

LC 301 Remove Invalid Parentheses — removable set shifts as string changes
minJumps prime-teleport — branch count varies per index
LC 291 Word Pattern II, LC 139 Word Break (brute) — branch = segment length, a range not a yes/no
📌 Constant → power. Fixed yes/no slots → 2^slots. Split-and-recurse-both-sides → Catalan sum. Nothing fits → say "exponential."

33 · 📊 Graph Edges (E) — Dense vs Sparse vs Tree

🚨 Sparse graph ≠ tree. A tree is a SPECIFIC TYPE of sparse graph.
Dense graph:  E = O(V²)     ← max for a simple graph
Sparse graph: E = O(V)      ← relatively few edges
Tree:         E = V - 1     ← always sparse

🎯 Values BETWEEN O(V) and O(V²) exist (V log V, V√V, 2V...) — but interviews only need the two bounds:

Sparse → O(V)
Dense  → O(V²)

📐 Union-Find TC follows the same split:

O(E · α(V))
Sparse → O(V · α(V)) ≈ O(V)
Dense  → O(V² · α(V)) ≈ O(V²)
📌 Tree ⊂ Sparse Graph ⊂ Graph. Sparse = O(V) edges, Dense = O(V²) edges. Don't think "sparse = tree" — think "tree is always sparse."

34 · 🔀 Backtracking — used[], Reuse and Duplicates: Ask 3 Questions Before the Loop

🎯 Before writing any backtracking code, answer three questions in order. Together they decide the whole loop: where it starts, what you recurse with, and whether you need used[] or a skip.

1️⃣ Does order matter?

Test with a tiny example: is [1,2] the same answer as [2,1]?

  • Different (order matters) → 🔴 Permutation → loop starts from 0 every call (any element can follow any element)
  • Same (order doesn't matter) → 🟢 Subset / Combination → loop starts from start (never look back at earlier indices)
🚨 Problem names LIE. "Combination Sum IV" is actually a PERMUTATION problem — LeetCode counts [1,2] and [2,1] as 2 separate ways, not 1. Trust the tiny example, not the title.

2️⃣ Can an element be reused?

// Combination: reuse is decided by what you recurse with
for(let i = start; i < n; i++) dfs(i, ...);       // reuse allowed  (Combination Sum)
for(let i = start; i < n; i++) dfs(i + 1, ...);   // no reuse       (Combination Sum II, Subsets)

// Permutation, NO reuse: used[] blocks an element already on the path (Permutations)
for(let i = 0; i < n; i++) {
    if(used[i]) continue;
    used[i] = true;
    path.push(nums[i]);
    dfs();
    path.pop();
    used[i] = false;
}

// Permutation, reuse allowed: no used[] at all (Combination Sum IV)
for(let i = 0; i < n; i++) dfs(...);
🚨 A permutation loop from 0 WITHOUT used[] lets the same element be picked again. That's right for Combination Sum IV, but in plain Permutations [1,2,3] it produces [1,1,1].

3️⃣ Does the input have duplicate values?

Sort first, then skip a repeated value at the SAME level of the tree:

nums.sort((a, b) => a - b);

// Combination / Subset (Subsets II, Combination Sum II)
if(i > start && nums[i] === nums[i - 1]) continue;

🔀 Permutations II (LC 47) — same sort, then two used[] checks:

for(let i = 0; i < n; i++) {
    if(used[i]) continue;                                             // already in my path
    if(i > 0 && nums[i] === nums[i - 1] && !used[i - 1]) continue;    // same value as left twin, twin not in my path
    used[i] = true; path.push(nums[i]);
    backtrack();
    path.pop(); used[i] = false;
}

🔁 Can't sort? Use a LOCAL Set instead (LC 491 Non-decreasing Subsequences — sorting would destroy the subsequence order). Create it INSIDE each call, right before the loop:

const seen = new Set();                        // fresh per call
for(let i = start; i < n; i++) {
    if(seen.has(nums[i])) continue;            // already tried this VALUE at this level
    seen.add(nums[i]);                         // never removed — no undo
    path.push(nums[i]); dfs(i + 1); path.pop();
}
🚨 The Set must be LOCAL (created inside each call): a shared Set would also block [4,7] after [4,6,7] used the 7, which is a different path and must stay allowed.
📌 Order → Reuse → Duplicates. Order picks the loop start (0 or start), reuse picks i vs i + 1 (or used[] for permutations), duplicates add sort + skip. Three answers give you the whole loop.

35 · ✂️ Palindrome Partitioning I vs II — Min Cuts = Min Pieces − 1

🎯 Don't treat "min cuts" as a new problem. It's the SAME dfs shape as counting/listing palindrome partitions — just optimize Math.min instead of collecting paths, then subtract 1 at the very end.

🔑 Why subtract 1 cutting a string into k palindrome pieces needs exactly k-1 cuts (fence-post logic — 3 pieces, 2 gaps between them).
"aab" → pieces: ["aa","b"] → 2 pieces → 1 cut

Same skeleton for both LC 131 (list all) and LC 132 (min cuts):

function dfs(start: number): number {
    if (start === n) return 0;              // 0 pieces needed for empty suffix
    let minPieces = Infinity;
    for (let end = start + 1; end <= n; end++) {
        if (isPalin[start][end - 1]) {
            minPieces = Math.min(minPieces, 1 + dfs(end));
        }
    }
    return minPieces;
}

return dfs(0) - 1;   // pieces → cuts
📌 Solve "minimum palindrome PIECES" (identical recursion to LC 131, swap path-collection for Math.min), then subtract 1 at the end to convert pieces → cuts.

36 · 🧭 Recursion → DP: Direction and Starting Index Come FROM the Recurrence

🎯 Workflow: write the recursion first, find its recurrence, then read direction + start straight off it — don't guess either one.

Direction — which way does the recurrence point?

dp[i] depends on dp[i+1], dp[i+2]... (LARGER index) → loop i: n-1 DOWN TO 0
dp[i] depends on dp[i-1], dp[i-2]... (SMALLER index) → loop i: 0 UP TO n

Starting index — ask ONE question: is this index's value already hardcoded, or does the recurrence still need to compute it?

Already hardcoded outside the loop (a true base case, e.g. dp[n] = 0)
  → loop EXCLUDES it, starts one step further in

Not hardcoded — computed BY the recurrence using a virtual sentinel
before/after the array (e.g. treating dp[-1] as 0)
  → loop INCLUDES it, starts right there

📐 Example — hardcoded base (excluded from loop):

dp[n] = 0;                          // base case, set once, outside
for (i = n - 1; i >= 0; i--) { ... }  // excludes n

📐 Example — computed via sentinel (included in loop):

// dp[i] built from dp[i-1], "nothing before index 0" = sentinel 0
for (i = 0; i <= n; i++) {
    dp[i] = (i === 0 ? 0 : dp[i - 1]) + something;
}
📌 Direction = which side the recurrence reads from. Starting index = the first slot NOT already hardcoded before the loop runs. Don't memorize "0 to n" or "n-1 to 0" as a rule — re-derive both from the recurrence every time.

37 · 🔗 LC 368 — Largest Divisible Subset

🎯 Asks: from nums, find the LARGEST subset where every pair (a, b) satisfies a % b === 0 or b % a === 0. Return the actual subset (not just its size).

🔑 The trick: SORT first. Once sorted ascending, you only need to check nums[i] % nums[j] === 0 for j < i — divisibility becomes transitive along the sorted order, so it reduces to an LIS-shaped DP (see #27's "committed rule" family): length[i] = longest divisible chain ENDING at i, plus a prevIdx[] array to reconstruct the actual subset (not just its length).
function largestDivisibleSubset(nums: number[]): number[] {
    const n = nums.length;
    nums.sort((a, b) => a - b);

    const length = Array(n).fill(1);
    const prevIdx = Array(n).fill(-1);

    let maxLen = 1;
    let lastChosenIdx = 0;

    for (let i = 0; i < n; i++) {
        for (let j = 0; j < i; j++) {
            if (nums[i] % nums[j] !== 0) continue;

            if (length[j] + 1 > length[i]) {
                length[i] = length[j] + 1;
                prevIdx[i] = j;
            }

            if (length[i] > maxLen) {
                maxLen = length[i];
                lastChosenIdx = i;
            }
        }
    }

    const res: number[] = [];
    while (lastChosenIdx !== -1) {
        res.push(nums[lastChosenIdx]);
        lastChosenIdx = prevIdx[lastChosenIdx];
    }

    return res;
}
📌 Sort → treat it as LIS but with % instead of > → track prevIdx[] alongside length[] to walk the chain backward and reconstruct the actual subset.

38 · 🍕 A % B when A < B → Always Just A

🎯 Smaller % bigger = the number itself. B goes into A zero times → nothing gets subtracted off.

2 % 6 = 2     3 % 10 = 3     1 % 2 = 1
🔑 Where this bites guessing % always "shrinks" a number — it doesn't, if the left side is already smaller than the right.
📌 A % B with A < B (both positive) → always A, untouched.

39 · 🔗 LIS-Family: Natural Recursion ≠ Standard DP (Different States, Not a Compression)

🎯 For LIS-shaped problems, the recursion you'd naturally write and the DP everyone actually uses are TWO DIFFERENT state definitions — the DP is NOT a rolling-array compression of the recursion's memo table.

🔴 Natural recursion dfs(i, prevIdx), take/skip:
dfs(i, prevIdx):
  skip = dfs(i+1, prevIdx)
  take = 0
  if condition(nums[i], nums[prevIdx]):
    take = 1 + dfs(i+1, i)
  return max(skip, take)

→ O(2ⁿ) raw. Memoized: state = (i, prevIdx) → O(n²) states × O(1) work = O(n²) time, O(n²) space.

✅ Standard/cleaner DP dp[i] = "best chain ENDING AT i", found by scanning j < i:
for i in 0..n:
  for j in 0..i:
    if condition(nums[i], nums[j]) and dp[j]+1 > dp[i]:
      dp[i] = dp[j] + 1

→ Also O(n²), but with O(n) space — a smaller, DIFFERENT state (dp[i] alone, no prevIdx dimension).

Problems in this family: LC 300 Longest Increasing Subsequence, LC 368 Largest Divisible Subset, LC 673 Number of LIS, LC 1027 Longest Arithmetic Subsequence (see #27) — all naturally tempt (i, prev) recursion, all have a cleaner dp[i]-ending-at-i standard solution.

🔑 The recursion you'd write first ((i, prevIdx) take/skip) and the DP everyone actually codes (dp[i] ending-at-i, scan j<i) are different STATE DEFINITIONS that coincidentally match on TC — not one compressed from the other.

40 · 🔗 LC 1027 — Longest Arithmetic Subsequence (tabulation)

🎯 Same "committed rule" family as #27 — state must carry the DIFFERENCE, not just the previous index, because a chain's diff isn't known until it has 2+ elements.

🔑 dp[i][diff] = length of the longest arithmetic chain ending at i with common difference diff. Diff can be negative (-500..500), so offset it to use as an array index.
function longestArithSeqLength(nums: number[]): number {
    const n = nums.length;

    // diff range -500 to 500
    const OFFSET = 500;

    const dp = Array.from({length: n}, () => Array(1001).fill(1));

    let ans = 1;

    for(let i = 0; i < n; i++) {
        for(let j = 0; j < i; j++) {
            const diff = nums[i] - nums[j];
            const key = diff + OFFSET;

            dp[i][key] = Math.max(dp[i][key], 1 + dp[j][key]);
            ans = Math.max(ans, dp[i][key]);
        }
    }

    return ans;
}

📐 Why dp[j][key] (same key, not a different one): nums[i]-nums[j] = diff means extending the chain ending at j with that SAME diff — so you read dp[j] at the SAME key. This is the tabulated form of #27's dfs(i, diff) recursion — dp[i][key] ending-at-i, same shape as #39's dp[i]-ending-at-i pattern, just with an extra dimension for the committed rule (diff).

📌 Offset negative diffs to use as array index; dp[i][diff] reads dp[j][sameDiff] — extending a chain means matching the SAME diff already locked in, not recomputing a new one.

41 · 🚨 || / && Short-Circuit SILENTLY Skips a Second Call With Side Effects

🎯 A || B and A && B don't always evaluate both sides — JS stops early the moment the result is already decided.

A || B → if A is truthy, B is NEVER CALLED (result already true)
A && B → if A is falsy,  B is NEVER CALLED (result already false)
🚨 This is invisible and dangerous when B is a function call with its OWN side effect (mutates state, unions a DSU, pushes to an array) — not just a pure boolean check.

📐 Where it bit — LC 1579 (Remove Max Edges, dual Union-Find for Alice+Bob):

if(alice.union(u, v) || bob.union(u, v)) edgesUsed++;   // ❌

If alice.union(u, v) returns true (union succeeded), bob.union(u, v) never runs at all — short-circuited. For a "shared" edge meant to help BOTH graphs, Bob's DSU silently misses the merge whenever Alice's happens to succeed first. No error, no crash — just a wrong final answer.

✅ Fix — call both FIRST, combine the booleans AFTER:

const usedByAlice = alice.union(u, v);
const usedByBob = bob.union(u, v);
if (usedByAlice || usedByBob) edgesUsed++;
🔑 The moment a ||/&& operand is a function call that MUTATES something (not just reads a value), short-circuiting becomes a correctness bug — call every side-effecting function separately first, THEN combine the results in a boolean expression.

42 · 🎯 "Group + Delete-Once" Kills Repeated O(n) Scans in BFS — and Why It's log(maxVal), Not n

🎯 Where this shows up: a BFS where one node can jump to MANY other nodes sharing some property (same value, same prime factor, etc.) — the naive version re-scans the WHOLE array from every such node, giving O(n²).

📐 Problem: LC 2059-style "Minimum Jumps" — jump i±1, OR jump to any index whose value shares a PRIME FACTOR with nums[i] (when nums[i] is prime).

🚨 Naive version (O(n²)) for every prime-valued node dequeued, loop over ALL n elements checking nextVal % currVal === 0. If many nodes share the same prime value, this SAME scan repeats from scratch every time — wasted, since the relationships never change.

✅ Fix — precompute buckets ONCE, then DELETE each bucket the first time it's used:

// prime -> [indices whose value has this prime factor]
const primeToIdx = new Map<number, number[]>();
// ...build once, before BFS...

// inside BFS, when processing currIdx with prime value currVal:
const nextIdxs = primeToIdx.get(currVal);
for (const idx of nextIdxs ?? []) { /* visit */ }
primeToIdx.delete(currVal);   // this prime can NEVER be expanded again
🔑 Why deleting is safe once you've pushed every index sharing that prime factor into the queue, there's nothing new to gain from expanding that same prime a second time — every node it could reach is already visited (or about to be).

📊 Why the resulting TC is O(n log maxVal), not O(n²):

  • Each bucket is now iterated exactly once, total, across the whole BFS (not once per matching node).
  • Total work = sum of ALL bucket sizes = total (index, prime) entries across every bucket.
  • Each number has at most O(log maxVal) DISTINCT prime factors — because if a number has k distinct primes, and every prime is ≥ 2, then number ≥ 2^k, so k ≤ log₂(number) ≤ log₂(maxVal).
  • So: n numbers × O(log maxVal) buckets each = O(n log maxVal) total entries = total BFS expansion cost.
📌 Whenever many nodes share edges through a common GROUPING KEY (prime factor, value, etc.), precompute buckets by that key and DELETE each bucket after its first use — this caps total work at "sum of bucket sizes," not "nodes × scan-per-node." And when the key is "distinct prime factors," that count per item is capped at O(log maxVal), since k distinct primes force the number to be ≥ 2^k.

43 · 🚨 1-Indexed Node Labels → EVERY Reference Needs the Same -1, Including the Source

🎯 When a graph problem gives nodes labeled 1..n but you build graph[]/dist[] as 0..n-1, EVERY single node reference from the input must get the same -1 conversion — not just the edges.

🚨 Easy to miss: the source/start node (often a separate parameter like k) gets forgotten, because it's not sitting inside the edge-list loop where the -1 conversion is already happening.
for(const [u, v, w] of times) {
    const nu = u - 1;   // converted
    const nv = v - 1;   // converted
    graph[nu].push([nv, w]);
}

pq.enqueue([0, k]);   // ❌ k still 1-indexed! forgot the same -1 here
dist[k] = 0;           // ❌ same bug — writes/reads the WRONG node entirely

📐 Why this fails silently, not loudly: if k happens to be the max label (k === n), dist[k] writes OUT OF BOUNDS (per #23 — JS never throws), creating a phantom extra slot nothing else reads. The REAL start node (dist[k-1]) never gets set to 0, so Dijkstra never expands from it — often surfacing as a wrong -1 ("unreachable") instead of a crash.

✅ Fix — convert it exactly like every other node reference:

const nk = k - 1;
pq.enqueue([0, nk]);
dist[nk] = 0;
📌 1-indexed input → 0-indexed internal structures means converting ALL node references consistently — edges inside a loop are easy to remember, but a standalone source/target parameter sitting OUTSIDE that loop is exactly where this -1 gets forgotten. Audit every place a raw input node label touches an array index.

44 · 🌳 Valid Tree — The Two Conditions, Two Ways to Check Them

🎯 A graph is a valid tree exactly when it is CONNECTED and ACYCLIC. Same fact, two equivalent lenses depending on how you're looking at the graph.

➡️ Directed / parent-pointer view (each node points to its parent)

  • Every node has at most one parent
  • Exactly one node has zero parents → that's the root
  • No cycles — a node can never be its own ancestor

🔗 Undirected / edge-count view (LC 261 Graph Valid Tree)

  • For n nodes, exactly n-1 edges
  • Graph is fully connected — one component
  • No cycles
🚨 "No two different edges between the same parent/child pair" is just the no-cycle rule in disguise — a duplicate edge between two already-connected nodes closes a 2-node cycle, same as any other cycle.
📌 Both views encode the same underlying fact — connected + acyclic — just counted differently: directed counts PARENTS PER NODE (max 1, exactly one with 0), undirected counts EDGES (exactly n-1) and checks connectivity directly. Pick whichever matches how the problem hands you the graph.

46 · 🍃 Recursion Tree — bᵈ Counts LEAVES, Not Every Node

🎯 2ⁿ (take/skip) and nᵈ (a for loop inside recursion) are the number of leaves. The tree has more nodes than that, but not a different big-O.

branching b ≥ 2, depth d
leaves = b^d
nodes  = 1 + b + … + b^d = (b^(d+1) − 1) / (b − 1)  ≤ 2·b^d

take/skip:    leaves 2^n,  nodes 2^(n+1) − 1   → still O(2^n)
permutations: leaves n!,   nodes ≈ e·n!         → still O(n!)

📐 Why: the last level is bigger than all the levels above it put together, so it decides the big-O.

⚖️ What actually changes the answer is the work per node:

  • ⚡ O(1) at every node → O(bᵈ)
  • 🍃 Real work only at the leaves (copy a path of length n) → O(n · bᵈ)
  • 🌲 O(n) at every node (slice, copy, join) → also O(n · bᵈ)
🚨 Only a chain (b = 1) breaks "nodes ≈ leaves": 1 leaf but d + 1 nodes. Count nodes only when work per node is not the same everywhere. See #2 and #32 for the bᵈ shapes.
📌 TC = (number of nodes) × (work per node). For b ≥ 2, nodes = O(leaves) = bᵈ, so the only thing left to ask is the work at each node.

47 · ✂️ Split Into k Pieces — k−1 Cuts, and Each Cut Leaves Room for the Pieces After It

🎯 A string of n characters has n − 1 gaps. k pieces = pick k − 1 gaps (3 pieces → 2 cuts 🔪🔪). This is the same fence-post idea as #35, here used to write the loop bounds.

🔪 Slice (cut positions)📦 Array (inclusive end)
Pieces[0,i) [i,j) [j,n)[0..i] [i+1..j] [j+1..n-1]
i1 to n − 20 to n − 3
ji + 1 to n − 1i + 1 to n − 2
for (let i = 1; i <= n - 2; i++)          // slice cuts
    for (let j = i + 1; j <= n - 1; j++) {}

for (let i = 0; i < n - 2; i++)           // array ends
    for (let j = i + 1; j < n - 1; j++) {}

🔒 Why the limits stop early: every piece after a cut needs at least 1 character. The 3rd piece needs 1 → j stops 1 early. The 2nd and 3rd need 2 → i stops 2 early. The array version is just the slice version shifted by 1.

🚨 Array version: j starts at i + 1 (not 0) and stops at n − 2 (not n − 1). Running j up to n and then writing if (j === n) break gives the same splits — that guard IS the "3rd piece can't be empty" rule — but putting the limit in the loop bounds is cleaner (LC 306 Additive Number).
📌 k pieces = k − 1 cuts. Each cut leaves room for the pieces after it. Slice → cuts in 1..n−1. Array → piece ends in 0..n−2. Number of splits = C(n−1, k−1) (n = 5, 3 pieces → 6).

48 · ↕️ Return Up vs Push Down — Where Does the Answer Travel?

🎯 Recursion has two ways to get an answer out, and many problems work with either. 🔙 Return up: dfs returns the answer "from here" and the parent combines it. ⬇️ Push down: dfs returns nothing, carries state in its parameters, and records the answer at the base case. (#45's "Read 1 = what I RETURN" is the return-up style.)

// Gold (LC 1219) as PUSH DOWN: carry the sum, update an outer variable
sum += grid[r][c];
best = Math.max(best, sum);                                // answer collected on the way down

// Paths III (LC 980) as RETURN UP: base case returns 1 or 0, parent adds
if (grid[r][c] === 2) return zeroCount === 0 ? 1 : 0;

❓ Pick with one question: "What does dfs(state) mean?" → "the answer for the subproblem from here" = return up. "I'm here with this path so far, report when you arrive" = push down.

♻️ Same rule in both: if you mutate a shared grid, undo before you return.

📌 Return = answers climb UP the stack 🪜. Push = state walks DOWN the stack 🚶. Only need a number → return up. Need every path → push down.
