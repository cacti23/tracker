🛤️ Delivery Framework

Most mid-level candidates don't fail for lack of knowledge. They fail because the clock runs out before they have a working system, and the feedback says "time management". The fix isn't going faster. It's a track to run on: 6 steps, in order. It's also your fallback when nerves hit.

⏱️ The track · tap a step

Steps 1–5 · make it work (functional requirements)

1📋 Requirements~5 min

Everything after this is measured against your requirements, so this is where you start. Requirements come in two kinds, and you need both:

🎯 Functional: what the system must do
⚙️ Non-functional: how well it must do it

🎯 A. Functional requirements: what it does

✍️ Write each one as "Users should be able to…". For an infra system with no end users (e.g. a rate limiter), the caller is a service: "Clients should be able to…".

🔎 How to find them 💬: go through the actors and ask three things:

👤 Who sends it?→📦 What do they send?→🎯 What outcome do they want?

🗣️ Then ask the interviewer like a PM: "does it need X?", "what if Y?".

✂️ Keep only the top 3. Twitter has hundreds of features. A long list hurts, and top FAANG companies grade you on choosing what matters.

🐦 Users should be able to post tweets➕ …follow users📰 …see tweets of people they follow

Now the twist. Picture two Twitters with exactly those 3 features. One has 100 users: a single server and one database are enough. The other has 100M users who expect their feed in 200ms: now you need caches, sharding, many servers. Same features, completely different design. What made the difference is how well it must work, and that's the second kind of requirement.

⚙️ B. Non-functional requirements: how well it does it

✍️ Write each one as "The system should be…". Pick the top 3–5, put each in context and give it a number.

❌ "low latency" (every system wants that)
✅ "search < 500ms" (which part, and the target)
🐦 availability > consistency100M+ DAUfeed < 200ms

🔎 How to find them: walk this checklist, so you don't blank. Remember it as FCC + SLEDS 💬. For each letter, ask its question; keep the 3–5 that really matter for this system.

F 🛡️ Fault toleranceA server or region dies: must it keep working?
C 🔀 CAPWhen the network splits, stay consistent or stay available? (Partition tolerance is a given.)
C 📜 ComplianceAny legal or industry rules on the data? (e.g. payments, personal data)
S 📈 ScalabilityHow many users and requests? Bursty (events, holidays)? Read-heavy or write-heavy?
L ⚡ LatencyWhich requests must be fast, and how fast? Focus on the heavy ones (e.g. Yelp search)
E 📱 EnvironmentClient limits: battery, memory, bandwidth (video on 3G)
D 💾 DurabilityCan we ever lose data? A social feed can lose some. A bank can't.
S 🔐 SecurityWho may see or change what? How is the data protected?

💬 Tips from the comments:

  • 🗺️ "Highly available" alone isn't enough. Say where, why and how. 🟢 Availability = fail open (most systems; quantify the eventual consistency, e.g. "< 1 min"). 🔒 Consistency = fail closed (money, double booking, 1 ride ↔ 1 driver). Still say "CAP": interviewers expect the term.
  • ⏱️ Guess latency targets from the client's point of view. For LLM chat, it's time-to-first-token.
  • ➕ Two more checks: 🔔 how real-time must updates be (ticket reserved, new bid)? ✨ What's unique here (LeetCode judge → isolate user code)?

Many guides tell you to do the math now. Don't, unless the answer changes a decision.

❌ DAU, QPS, storage → "ok, it's a lot". It only shows you can do arithmetic.
✅ TopK trending: number of topics → one min-heap or sharded?

🎤 Say: "I'll skip estimates and do the math when it changes the design."

2🧱 Core Entities~2 min

You know what to build. Now name the things it's built from. Core entities are the nouns of the system: what your API sends and your DB stores.

🔎 How to find them: read your functional requirements and pick out the nouns.

Users should be able to…

🐦 post tweets→👤 User · 🐦 Tweet
➕ follow other users→➕ Follow
📰 see tweets of people they follow→Tweet + Follow again, nothing new

💡 A Follow is a link between two users. You have to store it, so it's an entity too.

👤 User🐦 Tweet➕ Follow

❓ Also ask: who are the actors? Each one is usually an entity too (👤 User here).

Why bother? Because the next step gets easy: each entity usually becomes an API resource, so you can map entities to endpoints almost one to one.

🐦 Tweet→POST /v1/tweets · GET /v1/tweets/{id} ➕ Follow→POST /v1/follows 📰 (no entity)→GET /v1/feed: built from Tweet + Follow

⚠️ Not always 1:1: the feed isn't stored as its own entity, it's computed from others. That's fine. Use entities as the starting point, not a rule.

Keep it rough, as a quick list said out loud as a "first draft". You don't know what you don't know yet. Fields get added later, once you see what each request changes.

🏷️ Pick good names. Some interviewers check this ("one of the hardest problems in CS").

3🔌 API / Interface~5 min

Entities are the nouns. The API is what users can do with them. It's the contract your design must satisfy, and it usually maps 1:1 to the functional requirements.

⭐ RESTDefault. HTTP verbs on resources
GraphQLMany clients needing different data
RPC (gRPC)Internal service-to-service, when speed matters
WS / SSEReal-time, added after the core API

Don't overthink it: REST unless there's a reason not to.

POST /v1/tweets      {text}
GET  /v1/tweets/{id}  → Tweet
POST /v1/follows     {followee_id}
GET  /v1/feed        → Tweet[]

📦 Resources are plural nouns: tweets, not tweet.

🔐 Notice: there's no userId anywhere. The current user comes from the auth token, never from the body or path. Interviewers flag this.

4🌊 Data Flow (optional)~5 min

Only for pipelines. If data goes through a long chain of steps (crawlers, data processing), write the steps as a list. If not, skip it.

🕷️ Web crawler:Fetch seed URLs→Parse HTML→Extract URLs→Store data→🔁 Repeat
5🏗️ High-level Design~10–15 min

Now draw. The trick: don't design "Twitter". Satisfy one endpoint at a time, and the design builds itself 👇

📱 Client→🚪 API Gateway
✏️ Tweet CRUD Service→🗄️ Tweet DB (Postgres)id · authorId · text · media: s3Links[]
👥 Follower Service→🗄️ Following DB (Postgres)userId1 · userId2
📰 Feed Service→① getFollowers()
② getTweets(followers)

The big trap is adding complexity too early and never finishing. Keep it simple. Spot a cache or a queue? Say it, write a note, move on. It'll get its turn.

🗣️ Talk while you draw: how data flows, and what state changes on each request.

🗄️ Write the key fields next to the DB. Skip the obvious ones (name, email) and the types.

🖊️ Ask your recruiter which whiteboard tool you'll use (e.g. Excalidraw) and practice with it.

Step 6 · make it good (non-functional requirements)

6🔬 Deep Dives~10 min

Your design works, but the feed is slow: it fetches tweets from everyone you follow on every load. Good. That's exactly what deep dives are for. Go back to your non-functional list and harden.

✅ meet the non-functional requirements🧩 edge cases🚧 bottlenecks🎯 interviewer probes
100M+ DAU→ horizontal scaling · caches · DB sharding
Feed < 200ms→ fanout-on-read vs fanout-on-write + caches (the most interesting part of Twitter)

⚠️ Don't talk over the interviewer. They're looking for specific signals, and if you never pause, you miss them and lose points on communication.

Real interviews rarely wait politely for step 6. Often the interviewer jumps into a deep dive while your design is still half drawn. That's normal: the 6 steps are your default track, not a script they follow. 💬

🚨 When the interviewer jumps in early
1️⃣ 🙋 Go with them: it's where their signals are→2️⃣ 📍 Note what's unfinished, on the board→3️⃣ 🔙 Come back and finish it if time allows

"Sure. I'll note that the follow flow isn't drawn yet and come back to it."

"Happy to go deeper, but I may not finish the full design. Pause here, or keep going?"

🤔 Many interruptions can mean they doubt a choice. Answer with the reason, then check: "I'm using X because Y. Did you have a different concern?"

⚖️ The rule: they can pull you into a deep dive early. You shouldn't wander there on your own before the design works end to end. That's how candidates run out of time.

That's the loop: the first five steps get you a simple system that works. The last step makes it fast, scalable and reliable. Never the other way round, unless the interviewer pulls you there first.

🌐 Layers and the Life of a Web Request

Every design you draw is boxes talking over a network. Networking is a huge field ("one of the heaviest textbooks in school, gross"), but interviews need only a few layers and one story: what happens when you load a page. Learn that once and every arrow between boxes makes sense.

💡 Know 3 layers: IP (L3) routes, TCP / UDP (L4) deliver, HTTP and friends (L7) carry your app's data. One "request" is really many packets, and each one costs latency.

ℹ️ Note Networking weighs most in infra and distributed-systems interviews. Full-stack and product roles need a surface understanding. But if your interviewer just got off an oncall rotation fighting load balancer or CDN problems, be ready for probes.

🧱 7 layers, 3 that matter

Layers are abstractions. You don't need to know which voltage means 1 on the wire, only how to use the layer below. Like calling open instead of telling the disk how to read bytes.

🟦 Application = OSI 7 · 6 · 5, all inside your app

7⭐ Application 📱 where your app lives The language apps speak: HTTP (web), DNS (names → IPs), SMTP (email), FTP (files). Click Gmail → it talks SMTP and HTTP. ✉️ Like: what the letter says, in a language both sides understand. 📘 Article: DNS · HTTP · WebSockets · WebRTC. Built on TCP (on UDP for WebRTC)
6Presentation 🈯 the translator Gets the data into a shape both sides can read: format it (JSON, UTF-8), shrink it (gzip), lock it (TLS, the S in HTTPS, so hackers can't read it). ✉️ Like: translating the letter, folding it small, and sealing it in a locked envelope.
5Session 🗣️ the conversation manager Starts, keeps track of and ends one conversation. e.g. your login session: a cookie keeps you signed in across many requests. ✉️ Like: a pen-pal thread: "Re: our chat", so each letter belongs to the same conversation.

🟩 Transport = OSI 4

4⭐ Transport 📦 the delivery guarantee Splits data into numbered chunks and hands them to the right app by port. TCP checks every chunk arrived, in order, and resends lost ones. UDP skips the checks to be fast. ✉️ Like: mailing a book page by page with page numbers and a receipt for each (TCP), vs dropping flyers in mailboxes (UDP). The port is the flat number; the IP is the building. 📘 Article: TCP · UDP · QUIC. Reliability, ordering, flow control on top of IP

🟥 Internet = OSI 3

3⭐ Network 🧭 the GPS Writes the IP address on every packet. Routers pass it hop by hop, each one closer to that address: that's how your Netflix stream reaches you. No promises: packets can get lost, and TCP above fixes that. ✉️ Like: the address on the envelope, and sorting offices passing it city to city. 📘 Article: IP: routing + addressing, splits data into packets, . (InfiniBand too, for massive ML training)

🔁 NAT: on every packet that leaves home ➕ Adi's notes, checked; not in the article

Your phone has a private IP. The internet can't route it. So the router swaps it on the way out, every time. ☁️ AWS NAT Gateway: lets private servers reach the internet

  • ✅ Every packet to the internet is rewritten, both waysOut: the source becomes the router's public IP + a port. Back: the destination becomes your private IP again.
  • 🏠 Inside the home there is no NATPhone → printer stays on the local network, private IP to private IP.
  • 🆕 IPv6 usually needs no NATIt has enough addresses for every device to get a public one.
  • 🏢 A whole office can look like one IPThe server sees only the router's public IP. Rate limits or IP hash by IP treat 500 staff as one client.

🚚 TCP vs UDP

IP just throws packets at an address and hopes. Before an app can use them, someone has to decide: do we care if packets get lost or arrive out of order? That's the transport layer. In an interview it boils down to one choice: TCP or UDP.

💡 Default to TCP: reliable and ordered, and interviewers assume it. Pick UDP only when speed beats reliability, and say what browsers get instead.

The transport layer gives us guarantees "instead of handing us a jumbled mess of packets". Three protocols live here: TCP, UDP, QUIC. ⭐ The real choice is TCP vs UDP. Treat QUIC as "a better TCP" that isn't widely adopted yet.

✅ Remember Some performance-oriented interviewers are impressed by QUIC and HTTP/3. Most want you to spend your time elsewhere in the design.

"Reliable, in order" has a price. Watch what one lost packet does to everything behind it.

  • 🔢 Every packet is numbered; the ACK says "next I need #N"So when #2 is missing, every later arrival repeats "next I need #2" (duplicate ACKs).
  • ⏸️ Packets after the hole wait in the buffer#3, #4, #5 arrived, but the app can't have them until #2 does. This is head-of-line blocking.
  • 🔁 3 duplicate ACKs → resend at once (fast retransmit)No ACKs at all → the sender waits for a timeout, then resends (slower).
  • 🐢 Then the sender slows downTCP reads a loss as "the network is busy" and halves its sending window (🔗 ).

🚚 A numbered moving van: boxes 3, 4 and 5 arrived, box 2 fell off. You can't unpack in order until box 2 comes back, so 3, 4 and 5 sit in the hall. ➕ analogy not in the article

🚫 When connecting fails: timed out vs refused vs reset ➕ Adi's notes, checked; not in the article

Three errors, three causes. The error name tells you where to look.

  • ⏱️ Timed out: the SYN got no reply at allA firewall dropped it, the host is down, or the IP is wrong. Slow: the client keeps resending SYN until your connect timeout. Error ETIMEDOUT. ☁️ On AWS, check the Security Group: it drops silently
  • 🚫 Refused: the host answered RST, "nobody here"The machine is up, but nothing listens on that port: service down or wrong port. Fast, in milliseconds. Error ECONNREFUSED.
  • 💥 Reset: it was connected, then got RSTThe app crashed or restarted, or an LB or NAT forgot the connection after an idle timeout. Error ECONNRESET. Retry with backoff.

🚪 Knocking on a flat door: nobody answers (timed out), someone shouts "wrong flat!" (refused), or you were talking and the door slams (reset). ➕ analogy not in the article

🎯 Why would anyone want UDP?

No setup sounds great, but losing and reordering packets "kinda suck". So UDP wins only where speed matters more than reliability, and the client can cope with a missing packet.

📺 live video🎮 online gaming📞 VoIP📖 DNS lookups

🗓️ Old app versions live for months: a website updates on refresh, but users skip app updates. Each app version asks for just the fields it knows, so the backend can change without breaking old apps.

➡️ Web gets the same benefits, just smaller: fast network, always the latest code.

⚡ gRPC: efficient service-to-service calls

REST and GraphQL ship JSON text. When your own services call each other constantly, text gets expensive. gRPC is Google's (the "g") RPC framework: HTTP/2 + Protocol Buffers.

🧬 Protocol Buffers are "JSON with a more rigid schema", which makes them smaller and faster to parse:

message User {
  string id = 1;
  string name = 2;
}

📄 JSON { "id": "123", "name": "John Doe" }: 40 bytes, schema embedded

🧬 Protobuf: 15 bytes. Skinny tags, variable-length strings. "Less space and less CPU to parse!"

0A 03 31 32 33 12 08 6A 6F 68 6E 20 64 6F 65

🔎 Nit: 6A is a lowercase "j", so these bytes spell "john doe", not "John Doe".

service UserService {
  rpc GetUser (GetUserRequest)
    returns (GetUserResponse);
}
  • 🛠️ Definitions compile into client and server for many languages.
  • 🧰 Built for microservices at scale: streaming, deadlines, client-side load balancing.
  • ⭐ The key fact: it's binary, faster and more efficient than JSON over HTTP. Strong typing catches errors at compile time. Some benchmarks show 10x throughput.
  • 🔒 Use it for internal calls, when performance is critical or latency is dominated by the network, not the server's work.
  • 🚫 Not for public APIs or clients you don't control: binary, and the tooling is less mature than JSON over HTTP.
💻 Client⇄ Simple HTTP🖥️ Web Server⇄ gRPC⚡ High Performance Computation Server
💻 Client⇄ REST🔌 API Server⇄ gRPC🔒 Internal APIs
⚡ High Performance Computation Server⇄ gRPC🔒 Internal APIs

⭐ REST for public-facing APIs, gRPC for internal service-to-service, especially with binary data or when performance is critical. In many interviews, REST for both is fine. Build from there as the problem and the interviewer push.

✅ Remember Interviewers want to see how you think and react to new constraints, not an optimal whiteboard drawing. Don't hyper-optimise your RPC protocol before handling the real bottlenecks. "Premature optimization is the root of all evil!"

So: HTTP carries it, REST shapes it, GraphQL and gRPC are for specific needs. All of them are the client asking. Next: when the server has to speak first.

📡 Real-time: SSE, WebSockets, WebRTC

Everything so far is the client asking. But an auction, a chat or a video call needs the server, or another user, to speak first. gRPC can stream, but no browser supports it today. So the web has three tools, one for each shape of conversation.

💡 Server → client only: SSE. Both ways, high-frequency: WebSockets (justify them!). Audio/video calls: WebRTC, peer-to-peer over UDP.

📬 SSE: one response that never ends

Server-Sent Events is "a nice hack on top of HTTP": a spec that lets the server stream many messages, over time, in a single response.

❌ Normal HTTP
{ "events": [
  { "id": 1, … },
  …
  { "id": 100, … } ] }
Wait for the whole blob, then process it.
✅ SSE
data: {"id": 1, …}
data: {"id": 2, …}
…
data: {"id": 100, …}
Each line is its own message, handled on arrival.

⚠️ "Tradeoffs!" Some nasty, misbehaving networks batch all the SSE chunks into one response, which brings back exactly what we were avoiding.

✅ Remember Most interviewers don't know these limits and will gladly let you assume they don't exist. But anyone who has actually built SSE "has an enduring headache" from them, and may probe whether you've really used it.

🎯 Use it when clients should get notifications or events as soon as they happen, e.g. keeping auction bidders up to date on the current price. 🔗 Realtime Updates covers the server side.

🔌 WebSockets: both sides talk, any time

SSE pushes one way only. For real-time bidirectional traffic, WebSockets give a persistent, TCP-style connection with broad support, browsers included. The server pushes without a request, and so does the client. ☁️ Amazon API Gateway WebSocket APIs, or ALB

⚠️ Watch out A client being able to upgrade doesn't mean your infrastructure supports it. Every piece between client and server must support WebSocket connections. Anyone who's built them has fought firewalls, proxies and load balancers that don't.

🎯 Use them for high-frequency, persistent, bi-directional communication: real-time apps, games, anything that must send and receive the moment it happens. Just request/response, or SSE pushes are enough? Then WebSockets are overkill.

⚠️ Watch out Launching into WebSockets without justifying them is "a great way to get a thumbs down". The infra is expensive, and stateful connections at scale need significant accommodations in your design. Hold off unless you really need them!

🎥 WebRTC: browser to browser, no server in between

The third shape: two users talking to each other, not to you. WebRTC connects browsers peer-to-peer. It's built for video and audio calls, and it's the only app protocol here that uses UDP.

🚧 Peer-to-peer is harder: most clients don't allow inbound connections, and most users sit behind a NAT (network address translation) device. Two standard workarounds:

🪞 STUN

🔁 TURN

A relay: bounce traffic through a central server that routes it to the right peer.

🎯 ⭐ Use it for audio/video calling and conferencing. Collaborative editors? Occasionally, especially at scale. ⚠️ Watch out WebRTC is "an absolute pain to get right". Even the best implementations lose connections, and it's a niche solution. More candidates go wildly off trail designing peer-to-peer systems than build them successfully. Most problems don't need peer-to-peer. Stick to calls and conferencing and you'll be in good shape.

So: SSE when only the server talks, WebSockets when both do, WebRTC when the users talk to each other. Each one holds connections open. Next: spreading all those connections across many servers.

⚖️ Load Balancing

We know how one client talks to one server. But one server won't hold, so we scale. The moment there are three servers, every client has the same question: which one do I talk to?

🍽️ Think of a busy restaurant. One chef can't cook for the whole street, so you hire more chefs. Now every diner walking in asks: which chef cooks for me? This whole card is that question. ➕ analogy not in the article

💡 Horizontal scaling needs load balancing. Internal services: client-side (built into gRPC). Everything else: a dedicated LB. ⭐ L4 for WebSockets, L7 for HTTP.

Spread the load by deciding which server handles each request. Two ways: decide on the client side, or on the server side with a dedicated load balancer.

🧭 Client-side: the client picks

The client asks a service registry (directory) for the list of servers, then calls one directly. It polls, or gets pushed updates when servers are added or removed.

🍽️ Diners look at a board of free chefs by the door (the registry) and walk straight to one. No one stands in the way, so it's fast. But if the board is old, a diner may walk to a chef who just went home. ➕ analogy not in the article

⚡ Very fast: no extra network hop on every request, just a periodic sync of the server list. Two examples:

📖 DNS is client-side load balancing too. Each lookup of example.com returns a rotated list of IPs (a different order, or even a different set), so different clients hit different servers. ☁️ AWS Route 53: weighted or latency routing

📖 DNS is a phone book that lists the restaurant's numbers in a different order for each caller, so calls spread out. The catch: people keep the old page for a while (the TTL). ➕ analogy not in the article

ℹ️ Note DNS rotation is also how you avoid a single point of failure in the load balancer itself: run two LBs (in different data centers or regions, to be safe) and rotate between them in DNS. If one goes down, clients start trying the other.

So when does client-side work? It depends on how many clients must hear about changes, and how fast.

👥 Lots of clients?
No → ✅ Client-side can work · few clients you control: the Redis Cluster client, gRPC's client-side LB for internal services
Yes → ⏳ Tolerate update delays?
Yes → ✅ Client-side can work · e.g. DNS

⏳ Why "delays": update time grows with the number of clients to notify. DNS entries have a TTL (time to live), so far-flung DNS servers can cache them for their own clients, but your updates can never be faster than the TTL.

🎤 Great for internal microservices (built into gRPC). Interviewers rarely ask about the lines between your services, but if they do, mention client-side load balancing!

4️⃣ Layer 4: forwards connections, never reads

  • 🔗 Keeps persistent TCP connections between client and server. ☁️ AWS NLB
  • ⚡ Fast and efficient: minimal packet inspection.
  • 🙈 Can't route on application data.
  • 🎯 Used when raw performance is the priority, and for WebSockets and anything that needs a persistent connection. "If you're using websockets in your interview, you probably want an L4 load balancer."

☎️ L4 is a phone switchboard: it connects your call to one line and steps away. It never listens to what you say, so it can't route on it, but it's fast. A WebSocket is a long phone call: connect once, then talk for hours. That's exactly what a switchboard is for. ➕ analogy not in the article

7️⃣ Layer 7: reads every request

  • ✂️ Terminates incoming connections, creates new ones to the backends. ☁️ AWS ALB
  • 🔍 Routes on request content: URL, headers, cookies.
  • 🔥 More CPU-intensive (it inspects packets).
  • 🧰 More flexibility and features. Best for HTTP traffic: every protocol here except WebSockets.
  • ⚠️ It hides TCP details, but for persistent connections to the same server you still can't ignore the connection.

📨 L7 is a receptionist who opens every letter: "billing? → desk 3, support? → desk 5". Smart routing by what's inside, but reading costs time (CPU). For a long phone call there's nothing to read, so the receptionist just holds two lines open for hours. ➕ analogy not in the article

💥 Failures: plan for them

The other frequent deep dive. Servers crash, solar flares flip bits, power gets cut. The network fails too: cables get cut, routers fail, packets get dropped.

✅ Remember "The network is reliable" is one of the most dangerous assumptions in distributed systems. Always expect network calls to fail, be delayed, or return unexpected results.

🔁 Timeouts and retries with backoff

The most elementary hygiene: expect a call to take X, set a timeout, give up and try again. A temporarily slow server will likely answer the retry. But retries are double-edged: retrying requests that keep failing makes things worse. ☁️ AWS SDKs retry with exponential backoff + jitter by default

⏱️ Why your app sets the timeout: TCP won't ➕ not in the article

TCP guarantees delivery, not speed, so it will happily wait minutes. Your code decides how long is too long, with two timeouts:

  • 🔌 Connect timeout: how long to wait to open the connectionThe server is down or unreachable. Linux alone would keep trying for about 2 minutes.
  • 📨 Request timeout: how long to wait for the answer once connectedThe server is up but slow, like the bank in the cascade below.
// Node: give up after 2 s,
// then retry or fall back
await fetch(url, {
  signal: AbortSignal.timeout(2000),
})

📦 A courier guarantees your parcel arrives, but not by when. So you set your own deadline: "not here by Friday? I reorder."

⏳ Backoff: don't retry immediately. Wait a little, and longer after each failure, so the system can recover. 🎲 Jitter: add randomness, so clients don't all retry at the same moment "like a jackhammer".

📞 Calling a busy friend: no answer → wait 1 min, then 2, then 4 (backoff). If 1,000 people all redial on the exact same second, the line jams again; each waiting a slightly random time (jitter) spreads the calls out. ➕ analogy not in the article

🔑 Idempotency: retry without double-charging

Retries are cool, except when they have side effects. ⭐ This is why idempotent APIs are the key to safe retries: calling them many times gives the same result. GET is the classic one: the content may change, but fetching it doesn't change the system. For writes, add a key 👇

🔌 Circuit breakers: stop the cascade

Senior candidates often get "what happens when this service goes down?" Sometimes "fail and retry until it's back" is fine. But picture a database that went down cold and has to boot one instance at a time. A firehose of retries and angry users can pin each instance before it starts: a thundering herd. You can't get the first one up, so the whole DB never comes back. Stuck!

🛍️ Thundering herd = a Black Friday crowd at the doors: open one door and the crush knocks the first clerk over, so the shop never manages to open. ➕ analogy not in the article

✅ Remember Anyone who's done oncall has war stories about cascading failures: one failure creating new ones (it travels from a service to its callers). It usually goes unnoticed "until it bites you at 3am", which makes it a great interview question and a screen for experience. Prepare by learning to spot these cascades and how to stop them.

🛡️ The cascade toolkit

A breaker alone isn't the whole answer. Each tool fixes one step of the cascade above. ➕ bulkhead, shedding, queue: not in the article

  • ⏱️ Timeout · fixes ① Threads wait forever
    Give up after ~2 s, not 30. Hang up instead of holding the phone all day.
  • 🔁 Backoff + jitter, retry limit · fixes ④ Retries pile on
    Retry a few times, waiting longer and a little randomly. Never retry forever.
  • 🔑 Idempotency key · fixes ④ Retry charges twice
    Same order number → the bank charges once.
  • 🔌 Circuit breaker · fixes ② Still calling a broken service
    Stop calling after N failures, test again later. The house fuse.
  • 🚢 Bulkhead · fixes ⑤ One dependency eats every thread
    A separate, capped pool per dependency. A ship's watertight rooms: one floods, the ship floats.
  • 🚦 Load shedding / rate limit · fixes Too much traffic arriving
    Turn away extra requests early (fast 503) so the ones inside finish. A bouncer at a full club.
  • 🪂 Fallback · fixes User gets nothing
    Give a lesser answer: "Order placed, payment confirming", cached results, a default list.
  • 📬 Queue it · fixes Slow work blocks the user
    Accept the order now, charge from a queue. The bank's slowness no longer holds a user thread. ☁️ Amazon SQS

2️⃣ Don't wait: "Timeouts on every call, retries with exponential backoff and jitter, and an idempotency key so a retry can't double-charge."

5️⃣ Decouple: "If payment can be async, put it on a queue and charge when the bank recovers."

🔁 Backoff in numbers
  • Exponential = doubling: wait 1, 2, 4, 8 s. With jitter, one client retries after 1.7 s and another after 3.1 s, so 1,000 clients don't hit at once.
  • 🧮 Retry storm: if each of 5 layers makes 3 attempts, one user call becomes 3⁵ = 243 attempts at the bottom.
🐃 Thundering herd
  • DB restarts → 1,000 users retry at once → it crashes again → it never recovers. The same rush happens when a cache entry expires or a lock frees up.
🔑 Idempotency keys in practice
  • Store key → result (Redis or a DB table), atomically with the work. A retry with the same key returns the stored result without re-running anything.
  • Natural keys: user + order id for a payment; the unique email for sign-up (handle the unique-constraint error by returning the existing user).
  • ❓ Left open: who generates the keys, and how to stop collisions or forged keys. The article's "user + date" example is deliberately simple.

🧩 REST: Resources, Methods, Inputs, Outputs

A REST API is four decisions: what things exist (resources), what you do to them (methods), where the input goes (path, query, body), and what comes back (status + body).

🗄️ Think of a filing cabinet. Resources are the drawers (events, bookings). Methods are what you do with a file: read it, add one, replace it, edit it, shred it. ➕ analogy not in the article

📦 Resource modeling: nouns, not verbs

Start with the things. If you followed the Delivery Framework, your resources are simply your core entities. Ticketmaster: events, venues, tickets, bookings.

GET  /events                 # all events
GET  /events/{id}            # one event
GET  /venues/{id}            # one venue
GET  /events/{id}/tickets    # available tickets for an event
POST /events/{id}/bookings   # create a booking for an event
GET  /bookings/{id}          # one booking
❌ What users can do: book, purchase
✅ What exists: events, venues, tickets, bookings
ℹ️ Note Resources are always plural nouns: bookings, events, tickets. Most interviewers don't care, some do, and it costs nothing to get right.

Resources relate to each other (an event has tickets). Two ways to show that:

🪆 Nested path
/events/{id}/tickets
The relationship is required: "tickets" makes no sense without saying which event.
🔎 Flat + query
/tickets?event_id=123&section=VIP
The filter is optional: all tickets, one event's, or one event's VIP ones.
✅ Remember Quick test: if the query doesn't make sense without the relationship → path parameter. If it's one optional filter among many → query parameter. Interviewers care more that you pick the right resources than a perfect URL, but this shows good instincts.

🔧 HTTP methods: and which are safe to retry

With the resources named, each method says what you do to one. The key question for each is whether repeating it is safe: .

  • 📖 GET reads and changes nothing ✅ safe to repeat GET /events/{id}, GET /events.
  • ➕ POST creates a new one ❌ a repeat makes a duplicate POST /events/{id}/bookings with details in the body; the server assigns the id. 2 calls = 2 bookings.
  • 🔁 PUT replaces the whole thing ✅ safe to repeatReplaces the whole resource (or creates it). PUT /users/{id} with the full user. Same data twice, same final state.
  • ✏️ PATCH changes part of it ⚠️ safe or not, it depends PATCH /users/{id} with just the email. "Set email to X" is safe, "append to a list" is not.
  • 🗑️ DELETE removes it ✅ safe to repeat DELETE /bookings/{id}. It stays deleted, even though the 1st reply is 204 and later ones 404.

⭐ Why it matters: networks fail and clients retry. A retried GET, PUT or DELETE is harmless. A retried POST can create a duplicate booking, and a retried PATCH like "add 100" adds 200. Both are fixed by idempotency keys (Patterns 👇).

🗄️ Read a file, add a new file, swap the file for a fresh copy, fix one line in it, shred it. Shredding twice still leaves no file; adding twice leaves two files. ➕ analogy not in the article

📮 Passing data: path, query, body

Endpoints need input: which thing, which slice of it, and the data itself. Each kind has one home.

/events/123
/events?city=NYC&date=2024-01-01 · /events?page=2&limit=20
{ "tickets": [...], "payment_method": "credit_card" }

Path = structural (which endpoint). Query = modifier (how it behaves). Body = payload (complex data, or anything too large or sensitive for a URL). The first query parameter follows ?, the rest are joined with &.

POST /events/123/bookings?notify=true
{
  "tickets": [
    {"section": "VIP", "quantity": 2},
    {"section": "General", "quantity": 1}
  ],

}

123 in the path: you must say which event · notify in the query: optional behaviour · tickets in the body: the core data you create

📮 Sending a parcel: the path is the address (where it goes), the query is a sticky note ("ring the bell", "leave with neighbour"), the body is what's inside the box. ➕ analogy not in the article

📬 Returning data: status + body

A response is two things: a status code that says whether it worked, and a body (usually JSON) with the data.

✅ 200 OK🆕 201 Created🙋 400 Bad request🔑 401 Needs authentication🔍 404 Not found🔥 500 Server error

🔁 "PUT is idempotent" is a promise, not magic

🔍 GraphQL and ⚡ RPC: When REST Isn't Enough

REST has fixed endpoints with fixed shapes. That hurts in two places: many different clients wanting different data (→ GraphQL), and your own services calling each other millions of times (→ RPC).

🥗 GraphQL: why Facebook built it

2012: Facebook's mobile app needed different data than the web app, but REST endpoints returned fixed shapes. The mobile team kept asking for new or changed endpoints, slowing both sides.

😩 Option A: an endpoint per use case → endpoint sprawl, painful upkeep
🐘 Option B: one endpoint returns everything → mobile downloads megabytes it never uses (over-fetching)

✅ GraphQL: one endpoint that takes a query. The client defines the shape; the server returns exactly that shape, no more, no less.

query {
  event(id: "123") {
    name
    date
    venue { name address }
    tickets { section price available }
  }
}

Mobile asks for name + date only; the web dashboard asks for all of this. Same endpoint.

🥗 A salad bar vs set dishes: each client fills its own plate in one trip, instead of the kitchen inventing a new dish for every customer. ➕ analogy not in the article

ℹ️ Note Built in 2012, open-sourced in 2015: that's why the Networking card says 2015. Both are right. ➕ not in the article

🎯 When GraphQL, in an interview

GraphQL isn't "better REST". It solves one specific problem, so bring it up only when you hear that problem.

  • 👂 "The mobile app needs different data than the web app" or "avoid over- and under-fetching" → they probably want GraphQL.
  • 🏃 Frontend teams iterate without backend changes: a new field on a screen needs no new deploy, if the field is already in the schema.
  • 💸 The cost: query parsing, schema validation, and often sophisticated caching. ⭐ Otherwise REST is simpler.
✅ Remember Raise GraphQL when there's a clear over- or under-fetching problem, never as your default. Interviewers like that you know it, but prefer to see the core problems solved with simpler tools first.

With GraphQL you design a schema (types and how they relate) instead of endpoints. Relationships live in the schema, so a client can follow Event → Venue in one query.

📞 RPC: call a function over the network

GraphQL fixes the client side. Inside your system, services just want to call each other fast. RPC (Remote Procedure Call) lets a client call a procedure on a server and wait for the answer, without caring about the network.

🍽️ REST = resource-oriented: GET /events/123
📞 RPC = action-oriented: getEvent(eventId: "123")
// Instead of GET /events/123
getEvent(eventId: "123")
// Instead of POST /events/123/bookings
createBooking(eventId: "123", userId: "456", tickets: [...])

🧾 Protocol Buffers: one contract, typed code everywhere

The speed comes with a bonus: a written contract. You describe methods and data in a .proto file.

  rpc GetEvent(GetEventRequest) returns (Event);
  rpc CreateBooking(CreateBookingRequest) returns (Booking);
  rpc GetAvailableTickets(GetTicketsRequest) returns (TicketList);
}
// 📦 message = shape of the data
// 📤 what you send
message GetEventRequest {
  string event_id = 1;
}
// 📥 what comes back
message Event {
  // 1 = field number, not a value
  string id = 1;
  string name = 2;
  int64 date = 3;

  Venue venue = 4;
}
// CreateBookingRequest, Booking,
// GetTicketsRequest, TicketList:
// written the same way

📈 VPS: will it survive growth? (more versions, more data, more traffic)
  • Versioned: change the API without breaking old clientsOld mobile app versions live for years. Adding a field is safe; renaming, removing or changing a field's meaning is a breaking change → needs versioning.
  • Paginate any list that can grow, with a max page size"All bookings" works with 50 rows and dies at 5 million. Paginate from day one, and cap the page size so ?limit=100000 can't take down the DB.
  • Stateless: every request carries everything it needsToken, params, payload: all in each request (). Any server can handle any request, so scaling becomes a load-balancer problem. A big reason are popular. 💡 You show your ticket at every gate, so any guard can let you in.
🎯 PRICES: is each endpoint right?
  • Predictable: each method does exactly what its name says"Least surprise": GET never changes data, DELETE deletes, 200 means success (not "success": false inside a 200). 💡 A door marked "push" opens when you push.
  • Resources: name nouns, not actions (verbs)Writing /getUserBookings or /processPayment? Ask which resource it is: GET /users/{id}/bookings, POST /payments. The first thing interviewers look at.
  • Idempotent: a retry must never do the work twiceThe client can't tell if the server finished before the network broke, so it retries. GET, PUT, DELETE are naturally safe; POSTs for bookings and payments get idempotency keys 👇
  • Consistent: same names and shapes on every endpointSame names, params, response shapes. Not ?status=paid here and ?state=paid there. 💡 Every light switch in a house works the same way.
  • Errors say who is at fault and what went wrongRight status class (4xx "you messed up", 5xx "we messed up") + a machine-readable code + a human message.
  • Secure: every endpoint is locked unless opened on purposeAuth is opt-out: every endpoint needs a token unless deliberately public. Authorization checks this resource (John cancels only his own bookings). Rate limiting backs it up. 💡 Doors are locked unless marked "open".

🔎 Filtering and sorting

Once you paginate, clients want to choose which slice and in what order. Convention: query parameters.

/events?city=NYC&status=upcoming/events?sort=date?sort=-date = newest first

⭐ The work is consistency, not inventing names: if events filter by status, bookings do too (not state). One of the most common problems in real API reviews. In the interview, show one filtered endpoint and say "same conventions everywhere".

🔑 Idempotency keys: retry a POST safely

The scenario interviewers love: a user books tickets, the request times out, the client retries. If the first one worked, the user is now charged twice. "Just don't retry" isn't an answer: networks fail all the time.

POST /events/123/bookings
Idempotency-Key: 8e03978e-740c-4c2e-abd1-52f427d5c177
{ "tickets": [{"section": "VIP", "quantity": 2}] }

The client makes one unique key per logical operation. The server stores key → result; a retry with the same key gets the stored response. Same key, same result, no double charge. That's how Stripe handles payment retries.

🧾 Like an order number on a form: send it twice and the shop says "already have order #8e03, here's your receipt" instead of making a second order. ➕ analogy not in the article

🎤 ⭐ Raising this whenever your design has payments, bookings or orders is a strong signal: you think about failures, not just the happy path.

🧯 Consistent error responses

The status code gives the category. The body says what actually happened, in the same envelope on every endpoint.

{
  "error": {
    "code": "SEAT_UNAVAILABLE",
    "message": "Section VIP has only 1 seat remaining"
  }
}
  • 🤖 code: for machines, never changesA stable string the client branches on (the app shows a seat picker on SEAT_UNAVAILABLE).
  • 🧑 message: for people, free to change
  • 🎤 In the interview, say it in one sentence "errors return a consistent envelope with a machine-readable code."

🏷️ Versioning

APIs change, and public clients update on their own schedule. Versioning lets you change without breaking them.

⭐ URL: /v1/events, /v2/events. Explicit, visible, easy to route to different code.
📨 Header: Accept-Version: v2. Cleaner URLs, closer to HTTP standards, but less visible and harder to test in a browser.

🎤 Pick URL versioning unless asked about headers: more people know it, quicker to explain.

🔐 API Security: Who Are You, and What May You Do?

Security is often an afterthought in interviews, so a little awareness sets you apart. You don't need a bulletproof design: show you think about production, then move on.

💡 Two questions guard every request: who is this? (authentication) and may they do this? (authorization). Then a cap on how often (rate limiting).

🪪 Authentication vs authorization

The first question your API must answer: who is making this request, and are they allowed to do it?

🪪 : proves identity. "This is john@example.com."
🔑 Authorization: checks permission. "John may cancel his booking, not anyone else's."

🏨 A hotel: showing your passport at check-in is authentication. Your key card opening only room 412 is authorization. ➕ analogy not in the article

✅ Remember In most (not all) interviews auth isn't the focus. Say which endpoints need a logged-in user, and that you'd use a JWT or a session stored in a database.

🔑 API keys vs 🎫 JWTs

How the server knows who's calling depends on who the caller is: another program, or a person. Both ride in the same header (Authorization: Bearer …), but they work in opposite ways.

⭐ A JWT carries the info inside it. An API key only points to info stored on the server.
🎫 JWT: a signed card the user carries
  • ① You log in once, and the server signs a tokenIt checks your password, then writes your user id, role and expiry into a and signs it with its secret key. ☁️ Amazon Cognito issues JWTs
  • ② The client sends the token with every requestAuthorization: Bearer eyJhbGciOi…
  • ③ The server checks the signature, with no DB lookupChanged even one character? The signature no longer matches → rejected. Otherwise it reads the user straight from the token.
  • ⚠️ Signed, not encryptedAnyone can decode and read the payload. It only can't be changed. Never put secrets in it. ➕ not in the article
  • ⏱️ Short-lived, and hard to cancel earlyIt expires in minutes or hours. Since nobody checks a database, a stolen token works until it expires, unless you add a deny list. ➕ not in the article
// JWT payload: readable by anyone, changeable by no one
{ "user_id": "123", "email": "john@example.com",
  "role": "customer", "exp": 1640995200 }
🔑 API key: a random number the server looks up
  • ① The key itself holds no informationIt's just a long random string, like sk_live_abc123…. A password for an application, not a person. ☁️ Amazon API Gateway: API keys + usage plans
  • ② Every request means a lookup in the server's databaseKey → which account, what it may do, its rate limit. The info lives on the server, not in the key.
  • 🗄️ Stored as a hash, like a passwordThat's why OpenAI or Stripe show your key only once: they keep just a hash of it, so they can't show it again. ➕ not in the article
  • ♾️ Long-lived, and easy to cancelIt works until you delete it. Delete the row → it's dead on the very next request. ➕ not in the article

🗄️ Data Modeling ①: Database Model Options

Every design stores data somewhere. Data modeling decides what you store (entities), how each row is named (keys) and how rows connect (relationships). The bar is much lower than in a dedicated data modeling interview (common in data engineering loops): you don't need to normalize everything or draw a full schema diagram, just a schema that is clear, works, and fits the requirements. 🧭 Database Model Options

Pick the database type first, because it shapes how you store everything.

⭐ Resist showing off with exotic databases. Use a relational database (PostgreSQL) unless the requirements clearly ask for something else, or you have real experience and a strong opinion. Knowing when the others fit still shows trade-off thinking.

  • 📄 Document: one JSON document holds an entity and its nested dataMongoDB, Firestore, CouchDB.
  • 🔑 Key-value: one exact key gives one value, extremely fastRedis, DynamoDB, Memcached.
  • 📊 Wide-column: rows of time-stamped columns, built for huge write volumesCassandra, HBase.
  • 🕸️ Graph: nodes and edges, built for walking relationshipsNeo4j, Amazon Neptune. In interviews: almost never.

🔑 Key-Value Stores

Give an exact key, get one value back. Extremely fast, but you can't ask anything else: no "find by email", no joins.

  • 🤔 When to consider over SQL: you look data up by one idCaching, session storage, feature flags. Also very high write rates that need maximum speed and no complex queries.

📐 Data Modeling ②: Schema Design Fundamentals

The database type is picked. Now the real model: tables, keys, links and indexes, then the scaling choices. Each choice should trace back to a requirement, said out loud. That reasoning is what the interviewer scores.

💡 Three questions decide everything: how much data, how it's read, and how correct it must be right now. Then the tools answer them: keys and relationships (the links), indexes (fast lookups, like a book's index), normalizing (store each fact once, like one contact list), and sharding (split across machines, like library branches). 📇 Indexing for Access Patterns

An index lets the database find rows without reading every row. Say which columns you index, and why.

📖 The index at the back of a book: to find "normalization" you don't read every page. You look it up and jump to page 149.

  • 👤 Index on posts.user_id: quickly find all posts by a user
  • 🕒 Index on posts.created_at: load recent posts in time order
  • 🧩 Composite index on (user_id, created_at): load a user's recent posts efficientlyHow it works is just below 👇
  • 🐢 Every index slows writes a littleEach insert or update must also update every index on that table, so index what your queries need, not everything. ➕ not in the article
🧩 Composite index: use it from the left, with no gaps ➕ Adi's notes, not in the article

📒 A phonebook is sorted by surname, then by first name inside each surname. "Sharma" or "Sharma, Priya" is a quick jump. "Everyone called Priya" means reading the whole book.

CREATE INDEX ON posts
  (user_id, created_at);

-- stored sorted by user, then date:
-- user 1 → Jan 1, Jan 5, Jan 9
-- user 2 → Jan 2, Jan 3, Jan 8
-- user 3 → Jan 1, Jan 4, Jan 7
-- ✅ jump to user 2's block
WHERE user_id = 2

-- ✅ jump to the block, then Jan 3
WHERE user_id = 2
  AND created_at = 'Jan 3'

-- ✅ block is already in date order,
--    so no sort step
WHERE user_id = 2
ORDER BY created_at

-- ❌ Jan 3 is scattered in every
--    block: check them all
WHERE created_at = 'Jan 3'

Three columns, same idea: sorted by country, then city inside each country, then age inside each city.

CREATE INDEX ON users
  (country, city, age);

-- ✅ uses it
WHERE country = 'IN'

-- ✅ uses it
WHERE country = 'IN' AND city = 'BLR'

-- ✅ best case: all three
WHERE country = 'IN' AND city = 'BLR'
  AND age = 30

-- ❌ skips country
WHERE city = 'BLR'

-- ⚠️ country only: city is skipped, so
--    age-30 rows are spread over
--    every city in India
WHERE country = 'IN' AND age = 30
🧠 Rule: use the index from the left, with no gaps. It stops at the first missing column.
-- 🛒 my pending orders, newest first
-- index (user_id, status, created_at)
WHERE user_id = 7
  AND status = 'pending'
ORDER BY created_at DESC

-- 💬 last 50 messages in a chat
-- index (chat_id, sent_at)
WHERE chat_id = 9
ORDER BY sent_at DESC LIMIT 50

-- 📱 phones under ₹20,000, by price
-- index (category, price)
WHERE category = 'phone'
  AND price < 20000
ORDER BY price
🎯 How to choose the column order
  • 1️⃣ Columns compared with = go firstuser_id, status, chat_id, category.
  • 2️⃣ The range or sort column goes lastcreated_at, price. After a range ("under ₹20,000") the next column is no longer in order, so the index can't help with it.
  • 3️⃣ Shape it around your most common query

ℹ️ Postgres 18 and MySQL 8 can sometimes "skip scan" past a missing first column when it has few distinct values. Don't count on it in an interview. ➕ not in Adi's notes

✅ Remember Say it like this: "I'd create a composite index on (user_id, created_at), so the feed query filters by user and returns sorted results without a separate sort step."
✅ Remember Tie each index to an API endpoint: "GET /users/{id}/posts needs an index on posts.user_id." That shows you think about real query speed.

⚠️ Denormalized

🧹 Messy writes: every copy must change

⭐ Start with a clean normalized model and denormalize only when needed. Copied data wastes space and creates consistency problems that are much harder to fix than the speed problems you tried to avoid.

Denormalization can make sense in a few exceptions:

  • 📊 Analytics and reporting systemsThey aggregate data that changes rarely.
  • 🧾 Event logs and audit trailsThey capture a snapshot of the data at a point in time. (The address on an old order should not change when the user moves. ➕ example not in the article)
  • 🔎 Heavily read-optimized systems, like search enginesSpeed matters more than consistency.
  • ⚡ Or keep the database clean and copy into a cacheThe source of truth stays normalized. The cache holds pre-joined data, counts, or whatever shape makes reads fast (the flattened document in card ①).

📚 Scaling and Sharding

When the data outgrows one database, you shard it across machines. The skill is picking a split that keeps data read together on the same shard. ☁️ DynamoDB shards by partition key for you

🖥️ Server→→→🗄️ Shard 1 · posts 0–10k🗄️ Shard 2 · posts 10k–20k🗄️ Shard 3 · posts 20k–30k

🖼️ The lesson's picture: each shard holds a different range of posts

  • ⭐ Shard by the primary access patternMostly reading "posts by user"? Shard by user_id. One user's posts stay on one database, so the query touches one machine.
  • 🚫 Avoid cross-shard queries where possibleA timeline of posts from many followed users, sharded by user_id, means asking many shards and merging the results: slow and complex. (The usual fix is in the comments 👇)
  • 🔎 The picture splits by post range, which breaks the rule aboveOne user's posts end up on every shard. And if the ranges are of growing ids, every new post lands on the last shard. Read it as "the data is split", not as the design. ➕ not in the article
⚠️ Watch out Be careful with sharding by time range. It sounds good for "recent posts", but every new write goes to the shard for the latest time range: a hot shard. It's usually an anti-pattern for write-heavy systems. Time ranges suit archives and analytics, where recent data is read a lot but writes are spread out.
⚠️ Watch out The shard key is often permanent, and it affects every query. Think hard about the main access patterns before you choose it.

🗂️ Database Indexing ①: How Indexes Work · B-Tree · LSM · Hash

Database speed can make or break an app. Look up one user by email in a table of millions of rows with no help, and the database reads row after row until it finds a match: like checking every book in a library, one at a time, to find one novel. Indexes fix this. Knowing when to add one, on which columns, and of which type is a core interview skill. Mid-level engineers should know the basic strategies. Staff-level engineers should master the types and their trade-offs.

💡 An index is a separate structure built for searching, so the database jumps to the right rows instead of reading all of them (a book's table of contents). Each index type answers a different question: 🌳 B-tree for almost everything (the default), 📜 LSM tree for huge write volumes, #️⃣ hash for exact matches in memory, 🌍 geospatial for "near me", 🔤 inverted for words inside text (card ②), then composite and covering indexes to tune real queries (card ③). Explained below 👇

ℹ️ Note Indexing gets more attention in infrastructure-style interviews. Full-stack and product roles usually need only the basics: when and why to add an index. This lesson goes deeper, and the basics still help you design and tune your own apps.

🧠 How Database Indexes Work

Data ends up on disk as files. The main table is usually a heap file: a set of files cut into fixed-size pages (8KB in Postgres), with rows in no particular order, like a notebook where entries are written in the order they arrive.

💾 Physical Storage and Access Patterns
⚠️ Watch out Unless you interview for a database-internals role, you won't be asked about these details. They are still the reason indexes exist.
  • 💾 Data lives on disk, but can only be checked in RAMIt sits on SSDs. So every query must load pages from disk into memory first. What this means 👇
  • 🐢 No index = read every page, one by oneMillions of pages means millions of slow disk reads to find one row: flipping through every page of a huge book to find one word.
  • ⚡ An index says exactly which pages hold the dataIt gives a structured path straight to the data: the book's table of contents.
🧠 "Checked only in RAM": what it means ➕ not in the article

The CPU can only compare bytes that sit in RAM. It cannot look inside the disk. So to test one row (email = 'alice@x.com'?), the database first copies the whole page holding it from disk into RAM.

  • 📦 The disk hands out whole pages, never one rowNeed 1 row? You still copy its 8KB page. So the real cost of a query = how many pages it copies.

✍️ And an update? Change it in RAM, log it, write the page back later ➕ not in the article

Writes follow the same rule: the CPU can only change bytes in RAM. So an UPDATE never edits the disk directly. ▶️ Step through it:

  • 🧠 The change happens in the RAM copy of the pageCopy block 12 into the buffer pool (if it isn't already there), change the row there. The page is now dirty: the RAM copy is newer than the disk copy.
  • 📜 Before saying "done", append the change to the WAL on diskA small append to the end of one file (sequential, fast). That's what COMMIT waits for, not the 8KB page write.
  • ⏳ The dirty page goes back to disk later, in the backgroundMany changes to the same page become one write. Postgres does this in its background writer and at each checkpoint.
  • ⚡ Power cut? RAM is wiped, the WAL is notOn restart the database replays the WAL and redoes every committed change that hadn't reached its page yet. Nothing committed is lost.

Indexes aren't free. You pay on disk and on every write.

  • 📍 TID = (block number, offset)Block = which 8KB page of the heap file. Offset = which slot on that page. Postgres shows it as the hidden column ctid.
  • 🗂️ Slot → row, not byte → rowThe page starts with a list of small pointers (slots), and slot 3 says where row 3 sits inside the page. So a row can move inside its page without changing its TID.
  • 🔁 An UPDATE writes a new row version, with a new TIDPostgres keeps the old version for running transactions, so each index needs an entry for the new address too (skipped by a HOT update: no indexed column changed and the new version fits on the same page). One reason writes cost more with many indexes.
  • 🐬 MySQL InnoDB has no heap fileThe table itself is a B-tree sorted by primary key. A secondary index stores the primary key, not a TID, then does a second lookup in the primary-key tree.

🎟️ A cinema ticket: "screen 12, seat 3". The index is the box office that sells you the ticket. You walk straight to screen 12 and sit in seat 3, never checking other seats.

🏭 Real-World Examples

B-trees are used almost everywhere. PostgreSQL uses them for nearly everything: primary keys, unique constraints and most ordinary indexes.

CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE
);
-- 🌳 2 B-trees, built for you:
-- id (primary key) + email (unique)

⭐ Why B-trees are the default choice

The lesson gives five reasons. They fold into 3 S's: Sorted · Short · Steady. Each one is something a rival index lacks. ➕ grouping and rivals not in the article

📚SORTED
Keys stay in order, so ranges are free Find the start once, then read neighbours left to right. email = 'x' is just a range of size one, so exact matches and age > 25, ORDER BY all work. (lesson ①, ④)
❌ A hash index has no order: exact match only, no ranges.
📏SHORT
Hundreds of keys per node, so only 3–4 levels One node = one disk page, and each node has hundreds of children: 500 × 500 × 500 ≈ 125 million keys in 3 levels. 3–4 page reads to find anything. (lesson ③)
❌ A binary tree has 2 children per node: a billion keys = ~30 levels = ~30 disk reads.
⚖️STEADY
It balances itself, so speed never drifts A full node splits in two and pushes a key up. All leaves stay at the same depth, whatever the insert order and however big the table grows. (lesson ②, ⑤)
❌ A plain binary search tree fed sorted IDs (1, 2, 3…) becomes a long chain: lookups get slower and slower.

🧠 Say it in one line: "B-trees are sorted (ranges), short (few disk reads) and steady (self-balancing)."

✅ Remember "If you must pick an index in an interview, B-trees are a safe choice."

📜 LSM Trees (Log-Structured Merge Trees)

B-trees suit balanced workloads. Now picture DataDog taking in millions of metrics a second from thousands of servers. With a B-tree, every write means finding the right leaf page, reading it, changing it, writing it back. Fine at a few thousand writes a second; at 100,000 the random disk seeks become the bottleneck. ☁️ AWS: Keyspaces (Cassandra-compatible)

  • 🗄️ An LSM tree is the storage format of the whole table, not an index you addA B-tree index can go on any column. An LSM tree stores the whole table, sorted by the primary key, so primary-key lookups are very fast.
  • 🧩 Secondary indexes need extra structuresCassandra and DynamoDB (GSIs / LSIs) support them, but they perform differently from primary-key access.
  • ➕ It never edits in place: it only appendsBuilt for write-heavy work.
✍️ How LSM Trees Work

The trick: batch writes in memory, then flush them to disk in big sequential chunks. Many small random writes become a few large sequential ones.

  • 1️⃣ Memtable (memory component): new writes go into a sorted structure in RAMA red-black tree or skip list. Very fast: it's all in memory.
  • 2️⃣ Write-ahead log (WAL): every write is also appended to a log on diskFor durability. A sequential append, much faster than random writes.
  • 3️⃣ Flush to SSTable: a full memtable is frozen and written out in one goOften at a few MB. It becomes an immutable Sorted String Table (SSTable) on disk.
  • 4️⃣ Compaction: a background job merges SSTablesIt drops duplicates and deleted entries, so the file count stays small and reads stay fast.
🐢 Negative Impact on Reads

A B-tree finds any record in 2–3 disk reads. An LSM tree must check several places, newest first: ① the memtable, ② memtables waiting to flush, ③ every SSTable on disk, newest to oldest. Worst case, one lookup touches dozens of files.

  • 🌸 Bloom filters skip files that definitely don't have the keyEach SSTable has one. It answers "definitely NOT here" or "maybe". "Maybe" still needs a check, but the definite misses are skipped.
  • 📇 Sparse indexes skip blocks by key rangeSSTables are sorted, so each keeps the key range of every block. Want user_id 500 and a file holds 1000–2000? Skip the whole file.
  • 🧹 Compaction strategies trade one cost for anotherSize-tiered: less write amplification, more files to check. Leveled: fewer files, more frequent rewrites.
⚖️ Even with all three, LSM trees trade read speed for write speed. 🎤 Writes far more than reads (metrics, audit logs, IoT data)? LSM tree. A user-facing app where each page load runs several queries? B-trees usually win.

🌍 Database Indexing ②: Geospatial · Inverted Indexes

Two kinds of question a B-tree can't answer well: "what's near me?" (two dimensions) and "which posts contain this word?" (a word anywhere in the text). Both come up a lot in interviews: Uber and Yelp for the first, search for the second.

💡 🌍 Turn a 2D location into something a tree can search: a geohash (a PIN code for a map square), a quadtree (keep cutting the map into four) or an R-tree (boxes around groups of nearby things). 🔤 For text, flip it around: an inverted index maps each word to the documents that contain it, like the index at the back of a book. Explained below 👇

🌍 Geospatial Indexes

An odd quirk of interviews: geospatial indexes are quite specialized at work (you may never use one unless you deal with locations), yet they come up often, because of Uber, Yelp and Find My Friends. Proximity search is a favourite topic.

📍 The Challenge with Location Data

A Yelp-like app: millions of restaurants, each with a latitude and longitude. A user asks for "restaurants within 5 miles of me". The naive fix is two ordinary B-tree indexes:

CREATE INDEX idx_lat
  ON restaurants(latitude);
CREATE INDEX idx_lng
  ON restaurants(longitude);

long range

🖼️ The lesson's picture, simplified: red = every place at the right latitude, blue = every place at the right longitude. The 5-mile circle 📍 is the tiny part where they cross.

  • ❌ Latitude index first: you get a strip around the whole planetThen you check each restaurant's longitude one by one. The longitude index doesn't help: those are point lookups, not a range scan.
  • ❌ Both indexes together: two huge result sets to mergeTheir overlap is a rectangle much bigger than the circle, and you still filter out the far ones.
  • ❌ One composite (lat, lng) index: still a band scanIt's sorted by lat first. Two Bellevue restaurants at lat 47.61 and 47.62 are neighbours, but in the index every restaurant in the world between 47.61 and 47.62 sits between them. A query near New York (lat 40) reads Madrid, Beijing and Tokyo, then throws them away. (From the comments 👇)

⭐ So we need indexes that understand 2D closeness, instead of treating latitude and longitude as independent.

🧭 Core Approaches

Three come up in interviews: geohash, quadtree and R-tree. All keep nearby things together in the index. Interviewers mainly want you to explain why ordinary indexes fall short and reason about at least one fix; deep expertise in all three only matters for a location-data role.

🗺️ Finding a friend by latitude alone is like searching every house on the same line across the whole of India. You want "my neighbourhood", not "my latitude". ➕ analogy not in the article

🧩 Database Indexing ③: Index Optimization Patterns

Picking the index type is half the job. Experienced engineers study their app's read and write patterns, look at query plans and database metrics, and shape indexes around the queries that run most.

💡 Two patterns. 🧩 A composite index puts several columns in one sorted index, so one walk filters and sorts (a phone book sorted by surname, then first name). 📑 A covering index also stores the extra columns a query returns, so the table is never opened (the answer is on the index card). Then one flowchart to pick any index. Explained below 👇

ℹ️ Note The lesson uses SQL because it's the best-known language for databases. The same ideas apply to other databases, NoSQL included.

↔️ The Order Matters
  • ⬅️ An index helps only queries that use its columns from the left(user_id, created_at) is great for "user 123" and "user 123 after 1 Jan", useless for "created_at" alone. Full rule with examples: 🔗 Data Modeling ②.

📑 Covering Indexes

A covering index holds every column the query needs, not only the ones it filters or sorts on. Then the database never opens the table.

🐢 Regular index (user_id, created_at)
🌳 Finds the matching posts in the index
📄 Then opens each post's table page, just to read likes
Many extra disk reads to show one number
⚡ Covering index … INCLUDE (likes)
🌳 Finds the posts
✅ likes is already in the index
Answered from the index alone
-- regular index
CREATE INDEX idx_user_time
  ON posts(user_id, created_at);

-- covering: likes rides along
CREATE INDEX idx_user_time_likes
  ON posts(user_id, created_at)
  INCLUDE (likes);
  • ⚡ Best for frequent queries that need only a few columns of a big tableSocial feeds, leaderboards and other read-heavy features.
  • 💾 Cost: a bigger indexIt stores the extra columns. Often worth it when the query runs all the time.
  • 🔁 A column that changes often makes the index work harderEvery new like rewrites the index entry. Slightly stale counts are fine? Cover it. Likes change constantly, or you have many counters? Keep the index lean and read counts from a separate table or cache. (From the comments 👇)
⚠️ Watch out In 2026, covering indexes are more of a niche optimization than a go-to fix. Modern query optimizers run queries well with regular indexes. Covering indexes can give big wins in specific cases (read-heavy tables, few columns), but they cost storage and upkeep. In an interview, focus on simpler strategies; if you reach for a covering index, have a good reason. Unsure? Err on the side of simplicity.
