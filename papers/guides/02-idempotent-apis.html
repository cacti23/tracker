🔑 Making Retries Safe with Idempotent APIs

Malcolm Featonby · Amazon Builders' Library · Study guide for #2
🟢 Level 1 ⏱️ Original: 20 min ⏱️ Guide: ~25 min + 25 min lab 🔗 Read the original
🔗 #1 Timeouts & retries: retries are only safe if repeats are harmless 🔗 #8 Kafka: "at least once" delivery means consumers must dedupe 🔗 #23 Life Beyond Distributed Transactions: idempotent messages 🔗 #20 End-to-End: the end that knows the intent makes the key

⚡ TL;DR

🧩 The problem: your code calls an API that creates or changes something: an order, a payment, a server. The call times out. Did it happen or not? You can't tell. Retrying might do it twice: two orders, two charges.

🔁 Idempotent (safe to repeat): doing it twice has the same effect as doing it once.

🔑 Idempotency key (one id per intent): the client makes a random id once and sends it with the request and every retry. The server remembers which ids it has already handled.

🧾 Same answer for a repeat (a "semantically equivalent" response): the server answers a repeat with the same meaning as the first time, not an "already exists" error, so the caller never notices the retry.

⏳ Edge cases: remember keys long enough for late retries (not forever), and reject a key reused with different data.

👉 In one line: the client sends one key per intent and reuses it on every retry; the server saves the key and the result together and replays the result for repeats.

🗺️ The whole article in one flow: one "create" call, start to finish.

📱 1. Client makes a key once per intent ("pay ₹500 for order #123"), e.g. a random UUID.
↓
📤 2. Send the request with the key. No answer (timeout, 503)? Wait, then back to 2 ↺ with the same key.
↓

🔤 Terms first

Side effect
A change a call makes in the world: a row inserted, a card charged, an email sent, a server launched. A plain read has none.
Idempotent
Repeating it causes no extra side effects. "Set my plan to Pro" is idempotent (twice = still Pro). "Add ₹100 to my wallet" is not (twice = ₹200).
Idempotency key
A unique id the client attaches to one intent and reuses on every retry. The article calls it a client request identifier; EC2 calls the field ClientToken; Stripe and an IETF draft use an Idempotency-Key header. Usually a UUID: a random 36-character id like 7f3c9a1e-….
Fingerprint
A short hash of the request's data (e.g. SHA-256 of the JSON body), saved with the key so the server can tell "same request again" from "same key, different data".
409 / 422
HTTP status codes. 409 Conflict: "another request with this key is still running, try again soon". 422 Unprocessable: "this key was used with different data".
Duplicate request
A request the server already handled, arriving again: a retry, or a copy that was stuck in the network.
Reconciliation
Checking afterwards what really happened ("list my servers: is my job running?") and fixing differences. Slow, and often still unsure.
Validation error
The request itself is wrong (bad input, a 4xx). Sending it again gives the same error, so it's the one kind of error you don't retry.
Semantically equivalent response
Same meaning, not the same bytes. First reply: "server i-0abc, status pending". Repeat a minute later: "server i-0abc, status running". Same server, same outcome, current status.
Atomic (the A in ACID)
All or nothing. A database transaction either saves all its writes or none of them, even if the process crashes halfway.
At most once / exactly-once effect
"At most once" means never twice. Networks can deliver a request more than once, so the practical goal is an exactly-once effect: keep retrying until it works, and let the key make repeats harmless.
Late-arriving request
A copy of a request that shows up long after it was sent, e.g. stuck in a slow network path or a queue.
Retention window
How long the server remembers a key before deleting it.

🧠 Mental model

🍽️ The restaurant order slip. A waiter writes your order on slip #42 and takes it to the kitchen. He isn't sure the chef got it, so he brings slip #42 again. The chef sees #42 already on the spike and says "already cooking it". No second meal.

  • 🔑 The slip number is the idempotency key. The waiter (client) writes it, not the chef.
  • ❌ If a new waiter writes a new slip number for the same order, the chef cooks twice. That's a client making a new key per retry.
  • 🧾 If slip #42 comes back saying "2 coffees" instead of "1 coffee", the chef asks "is this a different order?" That's the parameter mismatch check.
  • 🗑️ The chef clears old slips at closing time. That's the retention window.

📖 How to read it. Each checkout tries once; a timed-out try is retried until it works. Of the timeouts, about a third each were a lost request, a crash midway, or a lost response. The server here does its work in one transaction, so a crash midway saves nothing.

👀 What to look for. Only the lost response case duplicates, because the work already happened. A new key per try is exactly as bad as no key: the server can't link the tries.

📖 Walkthrough

1. Why AWS retries everything, and the catch

What it says: big operations at Amazon are split into steps handled by smaller services. Launching an EC2 server, for example, calls services that pick a host, create an EBS disk, create a network interface, and start the VM. A controller drives every step to success. The simplest tool for that is to retry until it works, and many random faults go away on a retry (that's paper #1). It works so well that AWS SDKs (AWS's client libraries) retry automatically on network errors, server faults and throttling (being told "slow down", HTTP 429). That saves every caller from writing "undifferentiated boilerplate": the same failure-handling wrapper code everyone would otherwise write. The catch: a retry is only safe if it has no extra side effects. Retrying "create EBS disk" must not leave you with two disks.

What it means for you: your Nest services do the same. A checkout endpoint calls inventory, payments and shipping, and your HTTP client may retry for you (the AWS SDK does by default; libraries like axios-retry can). Every POST that gets retried, by you or a library, must be safe to repeat.

🧩 Primer: three ways a call can fail, and the client can't tell which

📤 Request lost on the way. The server never saw it. Nothing happened.
💥 Server crashed midway. Some work may have happened, unless it was all-or-nothing.
📥 Response lost on the way back. The work fully happened; you just didn't hear.

All three look identical to the client: a timeout. So a timeout means "unknown", not "failed". Retrying is right for the first, and wrong for the third unless the server can recognise the repeat. The widget above shows all three.

2. The singleton story: why the client can't fix this alone

What it says, step by step:

  1. 🧱 Setup. A customer runs a "singleton" workload: one that must have at most one EC2 server at any time. Their provisioning script (the code that sets up servers) asks EC2 to launch it.
  2. ⏱️ What goes wrong. The call times out. No response.
  3. 🤔 The dilemma. Is the workload running? Retrying might start a second copy, which could be very bad for a job that must only run once.
  4. 🔍 The workaround. Reconciliation: list what's running and work out whether the launch happened. That's a lot of work for a rare case.
  5. ❓ Still unsure. Even if a matching server exists, was it started by this script, or by another provisioning process?
  6. 💡 Lesson. The client can't make this safe on its own. The API has to help.
What it means for you: picture a nightly billing job that must run once. If "start billing run" times out and you blindly retry, every customer could be billed twice. Your Node code faces the same dilemma every time a POST times out.

3. The fix: make the operation idempotent

What it says: make the operation idempotent, so a request can be resent with no extra side effects. Then the API can promise clients something simple: any error that isn't a validation error can be retried until it succeeds. Client code gets much simpler. The complexity moves to the server, which now has to answer one question among many clients and many requests in flight: is this request a repeat of an earlier one?

3a. 🔍 How does the server spot a repeat?

What it says: one idea is a hash of the parameters: same caller, same parameters, so it must be a duplicate. No client changes needed. But it doesn't always hold. Two identical "create DynamoDB table" calls (DynamoDB is AWS's key-value database, and table names are unique) seconds apart are surely a retry. Two identical "launch an EC2 server" calls might be a customer who really wants two identical servers. Amazon's preferred way is a client request identifier: the caller adds a unique id to the request, and the same caller with the same id means a duplicate.

What it means for you: only the client knows its intent. "Send ₹500 to Priya" twice in a minute: a retry, or a second real transfer? A hash can't know. A key can: same key = same intent, new key = new intent.

✅ Why the key is better, from the article:

  • 🎯 Intent is explicit, so there are fewer surprises.
  • 📜 Auditable: the id shows up in logs like AWS CloudTrail (AWS's log of every API call), so you can trace what a request did.
  • 🏷️ Resources are labelled with the id. EC2's DescribeInstances (the API that lists your servers) shows the ClientToken each server was launched with. That answers the "mine or another process's?" question from the singleton story.

🤔 "Can't I just put a unique constraint on orderId?"

Yes, when your business rule already says "only one": one payment per order, one refund per return. That's a natural key, and the database rejects the duplicate for you. The idempotency key is the general tool for when no such rule exists, like two genuine ₹500 transfers to Priya. 🧠 My take: use a natural key when you have one, and an idempotency key for everything else. Note that a unique-constraint error is an "already exists" reply, which §3c explains is awkward for retries.

3b. 🔒 Save the key and do the work in one atomic step

What it says: on a request, the server checks whether it has seen this id. If not, it processes the request and records an idempotent "session" keyed by customer + id. If the same customer sends the same id again, the server knows it's a repeat. The key rule: recording the id and all the changes the request makes must be one ACID, all-or-nothing operation. Otherwise you can record the id but fail to create the resource, or create the resource but fail to record the id.

What it means for you: in Postgres, the key row and the order row go in one transaction. Try the two wrong orders below to see why.

🎛️ Try it: the server crashes between the two steps

📖 How to read it. The steps run top to bottom; 💥 is the crash. "Disks that exist" counts real disks after the retry.

👀 What to look for. Key first loses the work but reports success. Disk first creates a duplicate. Only one transaction gives exactly one disk.

🤔 "But my work calls another service. One transaction can't cover that."

Right. If the work is "charge the card at a payment provider", your database transaction can't roll back the provider's charge. The usual fix is keys all the way down: pass an idempotency key to the provider too (Stripe accepts one), save your progress in steps, and make each step safe to redo. Then a retry after a crash calls the provider again with the same key, and the provider replays the first charge instead of charging twice. Details and code in At work §3.

3c. 📨 What should a repeat get back?

What it says: say CreateResource with id 123 succeeds, but the response is lost. The client retries with 123. The server could reply ResourceAlreadyExists. That's technically idempotent: nothing extra happened on the server. But it hurts the caller in two ways:

  • ❓ Ambiguity: did my request create it, or someone else's?
  • 🔀 A side effect on the client: the caller's code takes a different path. They must handle "already exists" for something that, from their view, didn't exist when they called. So automatic retries inside an SDK no longer stay invisible.
What it means for you: in Nest terms, a retry that returns 409 Conflict where the first call would have returned 201 Created forces every caller to write special handling. That's the boilerplate idempotency was supposed to remove.

4. 🧾 Semantic equivalence: same meaning every time

What it says: for a given id, return a response with the same meaning as the first successful one, for some period. The EC2 demo shows it. Run run-instances from the AWS CLI without a token, and the response still contains a ClientToken: the CLI generated one. Repeat the call minutes later with that token and you get the same instance id, but its state now says "running" instead of "pending". Similar, not identical. The SDKs and CLI know which operations accept a token, add one when you don't, and reuse it on every retry. That keeps the "at most once" promise while your code never sees the retries.

Here's the shape of it, trimmed to the fields that matter:

// 1st call (times out on the client, but EC2 did launch)
{ instanceId: 'i-0abc', state: 'pending', clientToken: '7f3c…' }

// retry with the same clientToken, a minute later
{ instanceId: 'i-0abc', state: 'running', clientToken: '7f3c…' }
What it means for you: "same meaning" = same resource, same outcome. Fields that naturally change (status, timestamps) can be current. Build your HTTP client wrappers the same way: create a key per call when the caller didn't pass one, and reuse it across the wrapper's own retries.

🤔 "Do I store the whole response, or rebuild it?"

Either works if the meaning is the same. Replay (simplest): save the status code and body of the first result and send them back. Stripe does this. Rebuild from the resource's current state: what EC2 does, which is why the retry shows "running". Start with replay.

5. ⏳ Late-arriving requests

What it says, step by step:

  1. 📤 Client A creates a resource with key k1, and retries. The retry gets stuck in the network.
  2. 🗑️ Meanwhile, a second actor deletes the resource.
  3. 📬 The stuck retry with k1 finally arrives. What now?

The options: create it again (a resource someone deliberately deleted comes back, which is a surprise), return an error (confusing, since the client did nothing wrong), or do what EC2 does: honour the original promise and return the equivalent response, which now shows the server as terminated. Amazon calls this the "principle of least astonishment": when in doubt, do what surprises the caller least.

On retention, it says: the server must remember the first request to do this, but not forever. Storage grows, and a much later request could reuse an old id by accident and be wrongly matched. Each service picks its own window. For EC2 instances it's the lifetime of the server plus an extra interval, after which any late request has either arrived or no longer matters.

🔢 Worked example: retention vs retry window

  • 📬 A queue worker retries a failed "create payment" for up to 24 hours.
  • 🗑️ The API forgets keys after 1 hour.
  • 💥 A retry at hour 3 carries a key the server no longer knows, so it's treated as new: a second payment.

👉 Rule: retention > your longest retry window + delays. Stripe documents that keys can be removed once they're at least 24 hours old, so a client retrying for longer than that loses the protection.

6. 🧾 Same key, different data

What it says: if a known id arrives with different parameters, the safest assumption is that the customer meant something different. EC2 returns a validation error (a parameter mismatch). To check this, it stores the original parameters with the id.

🔢 Worked example: key k9 paid ₹500, then a client bug reuses k9 for ₹5,000. Three possible replies:

Server doesResult
Replay the ₹500 result❌ The client believes ₹5,000 was paid.
Charge ₹5,000❌ The key protects nothing.
Reject: "key reused with different parameters"✅ The bug surfaces at once. The IETF draft suggests HTTP 422.

In practice you store a fingerprint (a hash such as SHA-256 of the request body), not the whole body.

7. Conclusion: worth it where "at most once" matters

What it says: failures are normal ("expect the unexpected"), and handling them is necessary but undifferentiated work. Building on paper #1's automated retries, idempotent APIs give customers those retries while keeping the "at most once" promise. Customers like the simpler client code. But it costs time and complexity to build, and it isn't right for every API. Sometimes moving faster with a simpler contract is better for customers.

What it means for you: use it where a duplicate hurts: money, creating resources, sending messages, anything with a "once" rule. Reads don't need it, and neither do naturally idempotent writes like PUT /users/42/plan or DELETE.

🔀 If an assumption changes, what breaks:

  • 🌐 The work touches another system (a provider, an email service): one DB transaction no longer covers it. Use keys all the way down (At work §3).
  • 🔄 Clients make a new key per retry: zero protection.
  • ⏳ Retention is shorter than the retry window: late retries become duplicates.
  • 🪞 The key lookup reads from a lagging read replica (a read-only copy of the database that can be a moment behind): a quick retry may not see the key yet. 🧠 My take: read keys from the primary.
  • 👥 Keys aren't scoped per caller: two customers who pick the same key collide, and one could get the other's saved response. The article scopes by customer + id for a reason.

🌱 Then vs now

  • ✅ Still how AWS works: many AWS APIs take a ClientToken, and the SDKs and CLI add one for you (from the article).
  • 💳 Stripe (checked 2026-10-04): send an Idempotency-Key header on POSTs. Stripe saves the status code and body of the first result, even a 500 error, and replays it. It compares parameters and errors if they differ. Keys may be removed once they're at least 24 hours old. It doesn't save a result if validation fails or another request with the same key is still running, so those can be retried. GET and DELETE need no key.
  • 📄 IETF draft "The Idempotency-Key HTTP Header Field" (checked: draft-07, expired, not an RFC): recommends a UUID, and suggests 400 when a required key is missing, 422 when a key is reused with a different payload, and 409 while the first request is still running.
  • 🌐 HTTP itself defines GET, PUT and DELETE as idempotent and POST and PATCH as not. That's why the key goes on POSTs.
  • 📬 Queues: Kafka and SQS (AWS's queue service) deliver "at least once" by default, so consumers dedupe by message or event id. That's the same idea on the receiving end.
  • 🗣️ What to say today: "exactly-once effect: at-least-once delivery plus idempotent handling." Don't say the network or a queue gives you exactly-once delivery for free.

🛠️ At work

1. The client: one key per intent, reused on every retry

// payments.client.ts: calling a payments API from another serviceimport { randomUUID } from 'node:crypto';
import { HttpError, withRetry } from './retry'; // from guide #1

export function createPayment(
  api: string,
  body: { orderId: string; amount: number },
) {
  // ONE key per intent, made before the first attempt...
  const key = randomUUID();

  return withRetry(async (signal) => {
    const res = await fetch(`${api}/payments`, {
      method: 'POST',
      signal,
      headers: {
        'Content-Type': 'application/json',
        // ...and the SAME key on every retry.
        'Idempotency-Key': key,
      },
      body: JSON.stringify(body),
    });
    if (!res.ok) throw new HttpError(res.status);
    return res.json();
  });
}

Uses withRetry and HttpError from guide #1's retry.ts. In a browser or mobile app, create the key when the user taps Pay and keep it with the pending order, so a page reload or a second tap reuses it.

2. The server: a key table plus one transaction

-- schema.sql: the key tableCREATE TABLE idempotency_keys (
  caller_id   text        NOT NULL,
  key         text        NOT NULL,
  fingerprint text        NOT NULL,
  response    jsonb,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (caller_id, key)
);
// idempotency.service.tsimport { createHash } from 'node:crypto';
import { UnprocessableEntityException } from '@nestjs/common';

// Same shape as pg / PGlite: query() returns { rows }.
export interface Tx {
  query<R>(sql: string, params?: unknown[]): Promise<{ rows: R[] }>;
}
export interface Db {
  transaction<T>(fn: (tx: Tx) => Promise<T>): Promise<T>;
}

const fingerprint = (body: unknown) =>
  createHash('sha256').update(JSON.stringify(body)).digest('hex');

export class IdempotencyService {
  constructor(private readonly db: Db) {}

  /** Runs `work` at most once per (caller, key). */
  run<T>(
    callerId: string,
    key: string,
    body: unknown,
    work: (tx: Tx) => Promise<T>,
  ): Promise<T> {
    const fp = fingerprint(body);
    // One transaction: the key and the work commit together or not at all.
    return this.db.transaction(async (tx) => {
      const claimed = await tx.query(
        `INSERT INTO idempotency_keys (caller_id, key, fingerprint)
         VALUES ($1, $2, $3)
         ON CONFLICT DO NOTHING
         RETURNING 1`,
        [callerId, key, fp],
      );

      if (claimed.rows.length === 0) {
        // Seen before: answer from what we saved, never redo the work.
        const { rows } = await tx.query<{
          fingerprint: string;
          response: T;
        }>(
          `SELECT fingerprint, response FROM idempotency_keys
           WHERE caller_id = $1 AND key = $2`,
          [callerId, key],
        );
        if (rows[0].fingerprint !== fp) {
          throw new UnprocessableEntityException(
            'Idempotency-Key reused with different parameters',
          );
        }
        return rows[0].response;
      }

      const result = await work(tx);
      await tx.query(
        `UPDATE idempotency_keys SET response = $3
         WHERE caller_id = $1 AND key = $2`,
        [callerId, key, JSON.stringify(result)],
      );
      return result;
    });
  }
}
// payments.controller.tsimport {
  BadRequestException,
  Body,
  Controller,
  Headers,
  Post,
  Req,
} from '@nestjs/common';
import { IdempotencyService } from './idempotency.service';
import { CreatePaymentDto } from './dto/create-payment.dto';
import { PaymentsService } from './payments.service';

@Controller('payments')
export class PaymentsController {
  constructor(
    private readonly idem: IdempotencyService,
    private readonly payments: PaymentsService,
  ) {}

  @Post()
  create(
    @Headers('idempotency-key') key: string | undefined,
    @Body() dto: CreatePaymentDto,
    @Req() req: { user: { id: string } },
  ) {
    if (!key) {
      throw new BadRequestException('Idempotency-Key header is required');
    }
    // Keys are scoped per caller: two users may pick the same key.
    return this.idem.run(req.user.id, key, dto, (tx) =>
      this.payments.create(tx, dto),
    );
  }
}

Run on Node 22 against PGlite (Postgres compiled to WebAssembly): the first call created payment 1; the retry replayed it and the table still had 1 payment; reusing the key for ₹5,000 got a 422; a crash inside work rolled back the key and the payment together, and the retry then succeeded. The replayed reply came back from jsonb (Postgres's JSON column type) with its fields in a different order: same meaning, not the same bytes.

⚡ Two identical requests at the same moment? With this code in Postgres, the second INSERT waits until the first transaction commits, then hits the conflict and replays the saved result. If the first rolls back, the second does the work. Holding a transaction open during the work is fine when the work is quick database writes. It isn't when the work is a slow call to another service, which is the next section.

3. When the work calls another service: keys all the way down

🗄️ 1. Claim the key in its own transaction, with status started, and commit.
↓
🏦 2. Call the provider with a key (reuse yours). If this times out, retrying with that key is safe on their side too.
↓
💾 3. Save the provider's result and status done in one transaction.

💥 Crash after step 2? The retry finds the key still started, calls the provider again with the same key, gets the same charge back, and finishes step 3. Another request with that key while one is running gets 409 (or waits). Brandur Leach's write-up from his time at Stripe (Go deeper) builds this with a locked_at column (marks a key as being worked on) and "recovery points" (saved checkpoints, so a retry resumes where the last try stopped).

// inside step 2 (stripe-node accepts an idempotencyKey option)
const intent = await stripe.paymentIntents.create(
  { amount: 50_000, currency: 'inr' },
  { idempotencyKey: key },
);

✅ Code-review checklist

  • 🔑 Does every non-idempotent POST that can be retried take an Idempotency-Key?
  • 🔄 Is the key created once per intent, outside the retry loop?
  • 🔒 Are the key row and the business writes in one transaction?
  • 🧾 Is there a fingerprint check that returns 422 on mismatch?
  • 👥 Is the key scoped per caller (user, API client or tenant)?
  • ⏳ Is the retention window longer than the longest retry, including queue retries?
  • 🌐 If the work calls another service, does that call carry a key too?

📅 Try this week: find one POST in your codebase that a client, a queue or a library retries. Ask: if the response is lost and it's retried, what happens? If the answer is "a duplicate", sketch the key table for it.

🎤 In the interview

① Where it shows up

Any design with money or "do it once": payments and checkout, wallet transfers, ticket or hotel booking, ride requests, order placement, "send exactly one notification", webhook receivers, queue consumers, and the classic "design a payments API like Stripe".

② 30-second version

"A timeout means the result is unknown, so clients must retry, and retrying a write can do it twice. So I make writes idempotent: the client sends a unique idempotency key per intent and reuses it on retries. The server stores the key, a fingerprint of the request and the result in the same transaction as the write, replays the result for repeats, rejects a reused key with different data, and keeps keys longer than any retry window."

③ 2-minute version (say it out loud)

  • 🧩 Problem: request lost, crashed midway, or response lost all look like a timeout. Retrying a create can duplicate it.
  • 🔑 Key: client-generated (UUID), one per intent, reused on retries, scoped per caller. Hashing parameters can't tell a retry from a real second request.
  • 🔒 Atomic: the key and the writes commit together; otherwise you lose work or duplicate it.
  • 🧾 Reply: replay a response with the same meaning, not "already exists", so SDK retries stay invisible.
  • ⚠️ Edges: 422 on a parameter mismatch, 409 or wait while the first is still running, retention longer than the retry window, late requests get the original answer.
  • 🌐 Beyond one database: pass keys downstream to providers and dedupe queue consumers by event id.

④ "Design the Pay button for a food-delivery app"

↓ HTTPS "charge ₹500"

SDE1 answer
"I'll disable the button after the first tap, and check whether a payment already exists for the order before charging."
SDE2 answer

In the app:

  • 🔑 Create a key when Pay is tapped; keep it with the pending order; reuse it on every retry and after a reload. Disabling the button is UX only.

In the payments service:

  • 🗄️ Require Idempotency-Key (400 if missing). Table keyed by (user, key) with a fingerprint and the saved reply.
  • 🔒 Key and payment row in one transaction. Repeat → replay. Mismatch → 422. Still running → 409.
  • ⏳ Keep keys longer than the app's and the queues' retry windows (at least a day).

Toward the provider:

  • 🏦 Pass our key along, so our own retries can't double-charge; save progress as started → done.
  • 📬 Publish "payment.succeeded" with an event id; consumers dedupe on it.

⑤ Likely follow-ups

"Why not just dedupe by hashing the request body?"

Say: "Because two identical requests can be two real intents." Two ₹500 transfers to the same friend are both legitimate. Only the client knows whether it's a retry, so the client sends the key. That's exactly the RunInstances vs CreateTable example in the article.

"Two requests with the same key arrive at the same moment?"

Say: "The primary key on (caller, key) makes only one win." In Postgres the second insert waits for the first transaction, then replays its result. If the work is slow or external, mark the key started and return 409 to the second until it's done, as the IETF draft suggests.

"The provider charged the card, then your service crashed before saving. Now what?"

Say: "The retry calls the provider again with the same key." The provider replays the original charge instead of making a new one, and we save the result. That's why every hop that has side effects needs its own key (keys all the way down).

"How long do you keep keys, and where? Could you use Redis?"

Say: "Longer than the longest retry; at least 24 hours, like Stripe." Keep them in the same database as the data, so they commit together. Redis SET NX ("set only if it doesn't exist") with a TTL (an expiry time) is fine for best-effort dedupe (like not sending a notification twice), but it can't commit atomically with a Postgres write, so for money, use the database.

"Is exactly-once delivery possible?"

Say: "Not over a network that can lose replies. We get an exactly-once effect." That means at-least-once delivery (retry until it works) plus idempotent handling (repeats do nothing extra).

⑥ Red flags that cost points

  • "Disable the button" as the whole answer.
  • The server generates the key. It can't then link a retry to the first request.
  • The key is saved in Redis while the order is saved in Postgres, so the two aren't atomic.
  • Returning "already exists" or 409 on a successful retry.
  • Saying "Kafka gives exactly-once, so we're fine" without idempotent consumers.

⑦ Numbers worth knowing

  • ⏳ 24 hours: Stripe may remove keys once they're at least this old.
  • 🧮 122 random bits in a UUID v4: you'd need about 2.7 × 10¹⁸ keys for a 50% chance of any collision. In practice, never.
  • 🚦 400 / 422 / 409: the IETF draft's codes for a missing key, a reused key with different data, and a request still running.

⚠️ Traps

  • 🔄 A new key per retry (key made inside the retry callback). Fix: create it once, before the first attempt.
  • 🏭 Key made on the server. Fix: the client makes it; only the client knows its intent.
  • 🧩 Key in Redis, data in Postgres. A crash between them loses work or duplicates it. Fix: the same database, one transaction.
  • 🚫 "Already exists" on a retry. Fix: replay the first result (same meaning).
  • 🧾 No parameter check. A buggy reuse silently returns the wrong result. Fix: fingerprint, and 422 on mismatch.
  • ⏳ Retention shorter than retries. Fix: retention > longest retry window (worked example).
  • 👥 Keys not scoped per caller. Fix: primary key (caller, key).
  • 🖱️ Relying on a disabled button. It stops double taps, not timeouts, reloads or SDK retries.
  • ➕ Assuming PATCH is safe. "Increment by 1" in a PATCH is not idempotent; give it a key or make it "set to N".

✅ Check yourself

1. A "create order" call times out. Why can't the client just check and decide?

A timeout can mean the request was lost (nothing happened), the server crashed midway, or the response was lost (it fully happened). The client can't tell which. Checking afterwards (reconciliation) is extra work and still can't tell whether its own request or another one created the order.

2. Why is hashing the parameters fine for "create table" but wrong for "launch server"?

A table name must be unique, so two identical creates seconds apart must be a retry. Two identical server launches may be a real request for two servers. Only a client key expresses which one was meant.

3. The server saves the key, then creates the resource, and crashes in between. What goes wrong? And in the other order?

Key first: the retry sees the key and reports success, but no resource exists (lost work). Resource first: the retry doesn't see the key and creates a second resource (duplicate). Only one atomic transaction is safe.

4. Why is "ResourceAlreadyExists" on a retry worse than replaying the first response?

The caller can't tell whether its request created the resource, and its code must take a different path for something that didn't exist when it called. Automatic retries stop being invisible.

5. A key arrives again with a different amount. What should the server do?

Reject it as a validation error (422 in the IETF draft). Replaying the old result would mislead the client, and doing the new work would make the key meaningless. Store a fingerprint with the key to detect it.

🃏 Flashcards

Why can't the server dedupe by hashing the request?

Identical requests can be two real intents (two identical servers, two equal transfers). Only the client knows.

Where must the idempotency key be created?

On the client, once per intent, before the first attempt.

Why must the key and the work be atomic?

Key first + crash = lost work reported as success. Work first + crash = duplicate.

What's a semantically equivalent response?

Same meaning as the first reply (same resource and outcome), possibly with current fields like status.

How long should keys live?

Longer than the longest retry window plus delays. EC2: the resource's lifetime plus an interval. Stripe: may prune after 24 hours.
