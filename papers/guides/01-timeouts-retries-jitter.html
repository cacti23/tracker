⏱️ Timeouts, Retries & Backoff with Jitter

Marc Brooker · Amazon Builders' Library · 2019 · Study guide for #1
🟢 Level 1 ⏱️ Original: 20 min ⏱️ This guide: 15 min 🔗 Read the original

⚡ TL;DR

⏱️ Every remote call needs a timeout, or one slow dependency quietly eats all your connections and memory.

🔁 Retries are "selfish": they help you, but they add load, and during an overload they make things worse. Retry a little, in one layer only.

🎲 Back off exponentially and add randomness (jitter) so a thousand clients don't all retry at the same millisecond.

🧭 Why it exists

In a big system, something is always failing: a server, a network link, a load balancer, a deploy. Amazon's stance is don't try to prevent every failure; design so failures stay small.

Three tools do most of that work: timeouts (stop waiting), retries (try again), and backoff with jitter (try again politely). Each one is simple. The article is about how each one, used naively, causes the outage it was meant to prevent.

🧠 Mental model

🍽️ Think of a restaurant kitchen that's slammed. If every waiter re-shouts their order every 5 seconds, the kitchen gets slower, not faster. If every waiter waits exactly 30 seconds and then shouts together, it's still a wall of noise, just later. What works: each waiter waits a bit longer each time and picks a slightly random moment. The orders arrive spread out, and the kitchen catches up.

📖 Walkthrough

1. Failures happen

What it says: slow requests hold resources (memory, threads, connections, ports). Many failures are partial (some requests fail) or transient (fail briefly, then work). Traffic also arrives in bursts.

What it means for you: a hung call isn't "just slow". In Node, each in-flight request holds a socket, a DB pool slot, and memory for its closures. Enough of them and your healthy service falls over because of someone else's slow one.

2. Timeouts

What it says: set a connection timeout and a request timeout on every remote call. Pick the value from the downstream's latency data: choose an acceptable false-timeout rate, like 0.1%, and use the matching percentile, p99.9.

  • 🌍 Clients across the internet need room for worst-case network latency.
  • 📏 If p99.9 is close to p50 (a very tight service), add padding, or a tiny slowdown turns into a flood of timeouts.
  • 🧩 Make sure the timeout covers everything: DNS, TLS handshake, connecting, sending, reading. Use a well-tested client's timeout instead of rolling your own.
What it means for you: "p99.9" means 99.9% of calls finish faster than this. If the payment API's p99.9 is 350 ms, a ~400 ms timeout cuts off about 1 in 1,000 calls that would have succeeded, and in exchange you never hang for 30 seconds. Too high and the timeout protects nothing. Too low and you create retries, and possibly an outage, yourself.
🏭 The paper's 20 ms story: a service had ~20 ms timeouts. After every deploy, the first requests on new servers timed out, because the timeout also covered TLS connection setup, which took longer than 20 ms. Connections were reused afterward, so it only hit fresh servers. The first fix was a longer timeout for connection setup. The better fix was to open connections at startup, before taking traffic.

3. Retries and backoff

What it says: retries are selfish. They're fine when failures are rare and random. When failures come from overload, retries add load and slow recovery. Back off exponentially (wait 100 ms, 200 ms, 400 ms…) with a cap, and limit the number of retries.

  • 📚 Retries multiply across layers. Five layers that each try 3 times means up to 3⁵ = 243× the load on the database. Retry in one layer of the stack.
  • 🪣 Cap retries with a token bucket. Retries spend tokens; when tokens run out, retries fall to a fixed low rate. Amazon prefers this over circuit breakers, whose on/off modes are hard to test and slow to recover. The AWS SDK added this behavior in 2016.
  • 🔑 Only retry what's safe. Reads usually are. Creates usually aren't, unless the API takes an idempotency token, like EC2's RunInstances does. That's the whole subject of #2.
  • 🚦 Know which errors to retry. 5xx can succeed later; 4xx usually won't. Eventual consistency blurs this: a 404 can become a 200 once data replicates.
What it means for you: if your GraphQL resolver retries, your REST client retries, and the HTTP library retries underneath, you already have the multiplication problem. Pick one place.

4. Jitter

What it says: backoff alone keeps retries correlated: everyone who failed together retries together. Add randomness. And not just for retries: timers, cron jobs and periodic work cause spikes too, often hidden by per-minute metrics.

  • 🔁 For scheduled work, Amazon uses deterministic jitter: the same offset every time on the same host, derived from something like the host name. Overloads then repeat in a pattern humans can spot, instead of randomly.
  • 📉 EBS and Lambda saw clients firing every minute on the minute, or right after midnight. Spreading those out let them do the same work with less capacity.
What it means for you: a 0 0 * * * cron running on 20 pods hits your DB at the same second every night. A per-pod offset of a few minutes fixes it for free.

5. Conclusion

What it says: retry only when the dependency looks healthy, and stop when retries aren't improving availability.

What it means for you: retries are for blips, not for outages. During an outage, failing fast is the kind thing to do.

💎 Core ideas

  • ⏱️ No call without a deadline. Like a useEffect without cleanup: fine until it isn't, and then it leaks everywhere.
  • 🔁 Retries are a loan against the server's capacity. Borrow small, and never during a crisis.
  • 📚 Retries multiply per layer. Retry in exactly one place.
  • 🎲 Spread out anything that happens "at the same time": retries, crons, cache expiries, reconnects.
  • 🪣 Budget retries (token bucket) instead of trusting every caller to be polite.

⚖️ Tradeoffs

ChoiceYou gainYou give up
Short timeoutResources freed fast, quick failureFalse timeouts on slow-but-fine calls; more retries
Long timeoutFewer false failuresThreads/sockets held while you wait; slow user experience
More retriesHigher success on random blipsLoad amplification during overload; longer tail latency
Retry at the top layer onlyNo multiplicationRedoes work the lower layers already did
Random jitterSpreads loadHarder to reproduce timing bugs (hence deterministic jitter for crons)

If assumptions change: the advice assumes failures are mostly transient. If a dependency is hard down, every retry is pure waste. If your clients are not under your control (mobile apps, partners), you can't enforce jitter, so the server must protect itself with throttling and load shedding (#25).

🏭 Real world

  • From the paper: the 20 ms TLS timeout after deploys, the 243× multi-layer math, the AWS SDK token bucket (2016), EBS and Lambda clients synchronizing on the minute.
  • Today: AWS SDKs ship retry modes with exponential backoff, jitter and a retry token bucket. gRPC supports retry policies with throttling, and Envoy supports retry budgets. Same idea: retries capped as a share of normal traffic.
  • 🧠 My take: the most common version of this bug in web apps isn't in the backend. It's mobile and web clients reconnecting together after a deploy or a network blip. Every client's websocket or polling loop needs backoff with jitter too.

🛠️ In your stack

1. A timeout on every call

Many Node clients have no timeout, or a very long one, by default. Examples worth checking in your versions: axios defaults to no timeout, and pg pools wait forever for a connection unless you set connectionTimeoutMillis. Built-in fetch takes a signal:

const res = await fetch(url, { signal: AbortSignal.timeout(800) })

2. Retry with capped exponential backoff and full jitter

const sleep = (ms: number) => new Promise(r => setTimeout(r, ms))

export async function withRetry<T>(
  fn: (signal: AbortSignal) => Promise<T>,
  { attempts = 3, baseMs = 100, capMs = 2000, timeoutMs = 800,
    isRetryable = (_e: unknown) => true } = {},
): Promise<T> {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn(AbortSignal.timeout(timeoutMs))
    } catch (err) {
      if (attempt + 1 >= attempts || !isRetryable(err)) throw err
      // Full jitter: a random point between 0 and the capped exponential backoff
      const ceiling = Math.min(capMs, baseMs * 2 ** attempt)
      await sleep(Math.random() * ceiling)
    }
  }
}

// Only retry what can succeed later: timeouts, network errors, 5xx, 429.
class HttpError extends Error { constructor(public status: number) { super(`HTTP ${status}`) } }

const user = await withRetry(async signal => {
  const r = await fetch(`${API}/users/42`, { signal })
  if (r.status >= 500 || r.status === 429) throw new HttpError(r.status)
  return r.json()
}, {
  isRetryable: e => e instanceof HttpError || e instanceof TypeError ||
    (e as Error).name === 'TimeoutError',
})

This is a GET. For a POST that creates something, don't retry unless the API takes an idempotency key (#2).

3. A retry budget (the token-bucket idea)

// Retries spend a token; each success earns back a fraction.
// Net effect: retries stay a small share of real traffic, even during an outage.
class RetryBudget {
  private tokens: number
  constructor(private max = 10, private earnPerSuccess = 0.1) { this.tokens = max }
  trySpend() { if (this.tokens < 1) return false; this.tokens -= 1; return true }
  onSuccess() { this.tokens = Math.min(this.max, this.tokens + this.earnPerSuccess) }
}

4. Deterministic jitter for crons

import { createHash } from 'node:crypto'
import os from 'node:os'

// Same host, same offset, every night: spreads 20 pods over 5 minutes, reproducibly.
const offsetMs = createHash('sha256').update(os.hostname()).digest().readUInt32BE(0) % 300_000
setTimeout(runNightlyJob, offsetMs)

✅ Code-review checklist

  • Does every outbound call (HTTP, DB, Redis, queue) have a timeout, and does it cover connect + response?
  • Is there exactly one retrying layer for this call path?
  • Are retries capped (count and total time) and jittered?
  • Is the operation safe to repeat? If not, is there an idempotency key?
  • Do we only retry retryable errors (timeouts, 5xx, 429, network), never 400/401/403?
  • Do scheduled jobs and client reconnects have jitter?
🎯 Try this week: grep your service for axios.create, new Pool(, new Redis( and bare fetch(. List which ones have no explicit timeout and how many layers retry the same call. That list alone is a solid PR.

⚠️ Traps

  • "The library retries for me, so I'll add my own retry too." → Now you have 2 layers multiplying. Check what your SDK or client already does.
  • Timeout on the request but not on getting a pool connection. → Requests queue forever waiting for a DB slot. Time out both.
  • Retrying non-idempotent POSTs on timeout. → A timeout doesn't mean it failed. The order may exist; now it exists twice.
  • Backoff without jitter. → You've only moved the stampede a few seconds later.
  • Retrying forever "because it's important". → That's exactly how a 1-minute blip becomes a 1-hour outage.

🌱 Legacy

  • Not outdated at all. This is current practice, and it's built into AWS SDKs, gRPC and service meshes like Envoy.
  • The article's skepticism of circuit breakers is Amazon's view, not a universal law. Netflix popularized circuit breakers with Hystrix (now in maintenance mode), and many teams still use them. 🧠 My take: retry budgets and load shedding usually beat breakers, because they degrade gradually instead of flipping a switch.
  • What's missing: deadline propagation. Passing the remaining time budget down the call chain, so lower layers don't keep working on a request the caller has already given up on. The SRE book (#25) covers it.

✅ Check yourself

1. Why does the article call retries "selfish"?

A retry spends the server's capacity to raise your chance of success. That's fine when failures are rare. During overload, everyone's selfish retries add up to more load on a server that's already drowning.

2. API → service → DB layer → driver → DB, and each layer tries 3 times. Worst case?

3 × 3 × 3 × 3 = 81 calls to the database for one user action (243 with five retrying layers, as in the paper). Fix: retry in one layer, usually the one closest to the user or the one that knows the operation is idempotent.

3. How would you choose a timeout for a call to an internal pricing service?

Look at its latency percentiles. Decide what false-timeout rate you'll accept (say 0.1%), take the matching percentile (p99.9), and add padding if p99.9 is close to p50. Make sure it covers connect, TLS and response.

4. You already have capped exponential backoff. Why add jitter?

Clients that failed together back off by the same amounts and retry together, recreating the spike. With a cap, they even end up retrying at the same fixed rate. Jitter decorrelates them.

5. Your nightly report cron runs on 20 pods and the DB CPU spikes at 00:00. Fix?

Give each pod a deterministic offset (a hash of the host name, modulo a few minutes), or run the job on one leader. Deterministic beats random here, because the pattern repeats and you can debug it.

6. POST /orders timed out after 800 ms. Do you retry?

Only if the endpoint is idempotent, for example it accepts an Idempotency-Key so the server can spot the duplicate. Otherwise you may create the order twice, because a timeout doesn't tell you whether it ran. That's #2.

📝 Remember card

  • ⏱️ Every remote call gets a timeout, and it covers DNS, connect, TLS and response.
  • 📊 Timeout ≈ downstream p99.9, plus padding when the latency distribution is tight.
  • 🔁 Retry rarely, in one layer, only for retryable errors on safe operations.
  • 📈 Exponential backoff + cap + max attempts + full jitter.
  • 🪣 Budget retries as a share of traffic (token bucket).
  • 🎲 Jitter anything synchronized: crons, reconnects, cache TTLs. Use deterministic jitter for scheduled work.
  • 🚨 During an outage, failing fast beats retrying.
