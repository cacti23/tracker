🧠 1 · How to think (and invent it)

The one idea, restated bigger than the textbook: binary search works on any space where a yes/no test is monotonic — false, false, …, false, true, true, …. Each probe of the middle lets you throw away half the remaining space, because the answer can only be on one side. Sorted arrays are just the most common such space.

So stop memorizing the array version. Learn to ask: "what's my monotonic predicate, and what's the first x where it turns true?" Get that, and the loop is the same every time.

Mental checklist (1) what's the search space (array indices? a range of answers?) (2) what's the monotonic predicate over it? (3) when pred(mid) is true, is mid a possible answer (keep it: hi = mid) or already past it? If you can't articulate the predicate, you don't yet have a binary search.

Watch it get invented — First Bad Version

Versions 1..n are good then bad (once bad, always bad). One API call isBad(v). Find the first bad version with the fewest calls.

  1. Start brute. Call isBad(1), isBad(2), … → O(n) calls.
  2. Spot the structure. "Once bad, always bad" = monotonic. So isBad(mid) answers a half-space question: bad ⇒ the first bad is mid or earlier; good ⇒ it's strictly after mid.
  3. The leap. Keep [lo, hi] = the range still containing the first bad. Invariant: the answer is always inside [lo, hi]. Bad ⇒ hi = mid (mid might be it); good ⇒ lo = mid + 1 (mid is ruled out). Halve until lo == hi.
  4. Payoff. The range halves each step ⇒ O(log n) calls.

🧩 4 · The five core patterns

§4.2 is the keystone — learn that one template and 80% of binary search becomes a choice of predicate. Each pattern: a one-line model, a 🔑 invariant, a template, and a 🎤 interview lens.

4.1 · Classic — exact match

“Probe the middle; keep the half that could hold the target.”

Setup: sorted array, find target or -1. The textbook version uses a closed range [lo, hi] and while (lo <= hi).

🔑 Invariant — why it's safe The target, if present, is always within the closed range [lo, hi]. Each comparison removes mid and the proven-wrong half, shrinking the range while preserving the invariant. The range empties (lo > hi) only when the target isn't there.
// Classic exact search — returns index or -1
function binarySearch(a: number[], target: number): number {
  let lo = 0, hi = a.length - 1;          // CLOSED range [lo, hi]
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);    // floor, overflow-safe
    if (a[mid] === target) return mid;
    if (a[mid] < target) lo = mid + 1;    // discard left half + mid
    else hi = mid - 1;                    // discard right half + mid
  }
  return -1;
}
🎤 Interview lens Probed: the exact loop condition (<=) and both updates (mid±1); prove it terminates. · Escalation: exact → first/last occurrence (§4.2) → "count occurrences of x" (= upperBound − lowerBound).

4.2 · Boundary — find the first true (the master template)

“Find the leftmost x where predicate(x) flips to true.”

Setup: a half-open range [lo, hi] with while (lo < hi). When pred(mid) is true, mid might be the answer, so keep it (hi = mid); otherwise discard it (lo = mid + 1). At the end lo == hi == the boundary.

🔑 Invariant — why it's safe pred is false for everything below lo and (the answer aside) true at/above the boundary. The boundary always stays in [lo, hi]. Keeping mid on true and dropping it on false guarantees the range collapses onto the first true.
// THE template. lowerBound, upperBound, first-bad-version are all just a choice of `pred`.
function firstTrue(lo: number, hi: number, pred: (x: number) => boolean): number {
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (pred(mid)) hi = mid;     // keep mid — it might be the boundary
    else lo = mid + 1;           // drop mid — it's below the boundary
  }
  return lo;                     // == hi == first x with pred(x) true (or hi+1 if none in range)
}

// lowerBound: first index with a[i] >= target   |   upperBound: first with a[i] > target
const lowerBound = (a: number[], t: number) => firstTrue(0, a.length, i => a[i] >= t);
const upperBound = (a: number[], t: number) => firstTrue(0, a.length, i => a[i] >  t);
// count of t == upperBound - lowerBound ; exact search: i = lowerBound; present iff i<n && a[i]===t
🎤 Interview lens Probed: derive lowerBound vs upperBound from one template by changing only the predicate (≥ vs >); handle "not found" (returns n). · Escalation: insertion point → "Search Insert Position" → "Find First and Last Position" → range counting.

4.3 · On the answer — binary-search a feasibility predicate

“The array isn't sorted — but the answer space is. Search that.”

Setup: the input list isn't what you bisect. You bisect a range of candidate answers [lo, hi] using a monotonic feasible(x). "Smallest feasible x" = first true → reuse §4.2.

🔑 Invariant — the reframe If a capacity/speed/size x works, every larger x also works ⇒ feasible is false…false,true…true ⇒ the optimum is the first true. The "proof" you must give in an interview is exactly this monotonicity.
// Koko Eating Bananas — min speed to finish all piles within h hours
function minEatingSpeed(piles: number[], h: number): number {
  const hoursAt = (k: number) => piles.reduce((s, p) => s + Math.ceil(p / k), 0);
  let lo = 1, hi = Math.max(...piles);          // answer space: speed in [1, maxPile]
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (hoursAt(mid) <= h) hi = mid;             // feasible → try slower
    else lo = mid + 1;                           // too slow → must go faster
  }
  return lo;
}
🎤 Interview lens Probed: name the answer-space bounds and argue feasible is monotonic before coding. · Escalation: Koko → "Capacity to Ship Packages in D Days" / "Split Array Largest Sum" (same shape) → "Min days to make m bouquets."

4.4 · Rotated sorted array

“One half is always sorted — find it, then decide where the target lives.”

Setup: a sorted array rotated at an unknown pivot. At every step, exactly one side of mid is properly sorted; check whether the target falls inside that sorted side.

🔑 Invariant — why it's safe The target, if present, stays in [lo, hi]. Because one half around mid is fully sorted, a simple range check tells you definitively whether the target is in that half — so you can always discard the other half safely.
// Search in Rotated Sorted Array — distinct values
function searchRotated(a: number[], target: number): number {
  let lo = 0, hi = a.length - 1;
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (a[mid] === target) return mid;
    if (a[lo] <= a[mid]) {                          // LEFT half is sorted
      if (a[lo] <= target && target < a[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {                                        // RIGHT half is sorted
      if (a[mid] < target && target <= a[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return -1;
}
🎤 Interview lens Probed: which half is sorted, and the boundary <= in a[lo] <= a[mid]. · Escalation: search → "Find Minimum in Rotated Sorted Array" → with duplicates (LC 81: worst case degrades to O(n) — explain why).

4.5 · Peak — binary search with no target

“No target, no sort — just walk toward the higher neighbor.”

Setup: "Find Peak Element": a[i] != a[i+1], return any index that's larger than both neighbors (treat off-array ends as −∞). There's no value to match — you steer by the local slope.

🔑 Invariant — why it's safe If a[mid] < a[mid+1], the rising slope guarantees a peak somewhere to the right, so lo = mid + 1 still contains one. Otherwise a peak is at mid or left, so hi = mid. A peak always lives in [lo, hi]. (And mid+1 is safe: lo < hi ⇒ mid < hi.)
// Find Peak Element — O(log n), array not sorted
function findPeak(a: number[]): number {
  let lo = 0, hi = a.length - 1;
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (a[mid] < a[mid + 1]) lo = mid + 1;   // uphill to the right → peak is right
    else hi = mid;                           // downhill (or flat-down) → peak is here/left
  }
  return lo;                                  // lo == hi == a peak
}
🎤 Interview lens Probed: why moving toward the higher neighbor always keeps a peak in range, and why it's O(log n) with no sorted input. · Escalation: 1D peak → "Peak in a 2D grid" (binary-search columns) → "Find in Mountain Array."

The halving argument Each step discards ≥ half the remaining space, so the range of size N is gone in ⌈log₂ N⌉ steps. For "on the answer," N is the value range, not the array length — so bounds like [1, 10⁹] still finish in ~30 probes.

⚠️ 6 · Pitfalls — and the test that catches each

BugThe input that exposes it
mid = (lo + hi) / 2 overflows in fixed-int languages (Java/C++).Huge indices near INT_MAX → use lo + (hi − lo) / 2.
Infinite loop: lo = mid on the "keep" branch (should be hi = mid).Any 2-element range where mid == lo → lo never advances.
Mixing the two templates: closed [lo,hi] + while(lo<hi), or half-open + mid−1.Single-element array → off-by-one or skips the only candidate.
Forgetting the "not found" check after lowerBound.Target larger than all → returns n; indexing a[n] is out of bounds.
Rotated: a[lo] < a[mid] instead of <=.2-element rotations like [3,1] → wrong half chosen.
On-the-answer: hi initialized too small to contain the optimum.Koko with one giant pile → optimum = that pile; a smaller hi misses it.
Predicate isn't actually monotonic.Any non-monotone feasible → the boundary is undefined; binary search returns garbage.
🔗 This pattern, elsewhere Binary search is the converging pointer on the answer space — the same "discard half, safely" invariant as the converging two-pointer in two-pointers.html, but the space is values/answers, not array ends. The boundary template is bisect (Python) / lower_bound (C++). "On the answer" turns optimization into a yes/no decision — the seed of parametric search and several DP/greedy speed-ups. Rotated search is a cousin of finding the pivot / minimum in a rotated array.
