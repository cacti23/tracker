🪟 Sliding Window

A learning sheet — turn O(n²) subarray scans into one linear pass by reusing the window you already built.

🧠 1 · How to think (and invent it)

The one idea: a contiguous sub-array/sub-string answer depends on a window [left, right]. Instead of rebuilding every window from scratch (O(n²)), slide: when right moves one step, you only add one element; when you must shrink, left only ever moves forward. Each index enters and leaves the window once ⇒ O(n).

The whole topic is one question: "when is my window valid, and which end do I move to fix it?" Answer that with an invariant and the template writes itself.

Mental checklist (1) what does the window state track (a sum? a frequency map? a distinct count?) (2) what makes it invalid? (3) when invalid, you shrink from left; when do you record the answer — while valid, or after restoring validity? That last choice is the whole difference between "longest" and "shortest."

Watch it get invented — Longest Substring Without Repeating Characters

  1. Start brute. Check every substring for uniqueness → O(n²) or worse.
  2. Spot the waste. If [left, right] has no repeat and you push right, you don't re-scan the whole thing — you only need to know if the new char already sits in the window. And when it does, sliding left backward is pointless: any earlier start contains the duplicate too. left only moves forward.
  3. The leap. Keep lastSeen[char]. On each right, jump left to max(left, lastSeen[c] + 1) — past the previous copy. Record right − left + 1.
  4. Payoff. Each index is visited by right once and by left once ⇒ O(n).

🧩 4 · The five core patterns

Each = a one-line model, a 🔑 invariant, a template, a picture, and a 🎤 interview lens. The two variable templates differ in one line — where you record the answer.

4.1 · Fixed window — size k

“Add the newcomer, drop the one that fell off the back.”

Setup: maintain a running window state for exactly k elements. Each step is O(1): add a[right], and once the window is full, subtract a[right−k].

🔑 Invariant — why it's safe After processing index right, the window state describes exactly a[right−k+1 .. right]. Because you remove precisely the element leaving and add the one entering, the state is always a faithful summary of the current k-window.
// Maximum sum of any size-k subarray
function maxSumK(a: number[], k: number): number {
  let sum = 0, best = -Infinity;
  for (let right = 0; right < a.length; right++) {
    sum += a[right];                 // add newcomer
    if (right >= k) sum -= a[right - k];  // drop the one that fell off
    if (right >= k - 1) best = Math.max(best, sum); // window is full
  }
  return best;
}
🎤 Interview lens Probed: each slide must be O(1) — no re-summing the window. · Escalation: sum → average → "permutation/anagram in string" (a fixed window with a 26-length frequency match) → "first negative in every window" (a queue of negatives).

4.2 · Variable window — longest valid

“Grow greedily; shrink only while broken; measure after.”

Setup: expand right every step. If the window became invalid, shrink from left until it's valid again — then record the length.

🔑 Invariant — why it's safe At the end of each iteration, [left, right] is the longest valid window ending at right. Since left only moves forward, a window that became invalid can't be fixed by an earlier left — so we never miss a longer valid window.
// Longest substring with at most K distinct characters
function longestKDistinct(s: string, k: number): number {
  const count = new Map<string, number>();
  let left = 0, best = 0;
  for (let right = 0; right < s.length; right++) {
    count.set(s[right], (count.get(s[right]) ?? 0) + 1);  // grow
    while (count.size > k) {                               // shrink WHILE invalid
      const c = s[left++];
      const n = count.get(c)! - 1;
      if (n === 0) count.delete(c); else count.set(c, n);
    }
    best = Math.max(best, right - left + 1);               // record (now valid)
  }
  return best;
}
The famous trap — Longest Repeating Character Replacement Window is valid when windowLen − maxFreq ≤ k. The intentional bug everyone questions: maxFreq is never decreased on shrink. It can go stale — and that's fine, because a longer answer needs a larger maxFreq anyway, so a stale value never lets the window grow falsely.
🎤 Interview lens Probed: why does left never move backward (prove the amortized O(n))? · Escalation: no-repeat → at-most-K-distinct → "Max Consecutive Ones III" (≤ k zeros) → "Longest Repeating Char Replacement" (the stale-maxFreq argument above).

4.3 · Variable window — shortest valid

“Grow until valid; then squeeze as much as it stays valid.”

Setup: mirror of 4.2. Expand until the window is valid; then shrink from left while still valid, recording the length during the shrink.

🔑 Invariant — why it's safe Every time the window first becomes valid, the inner loop shrinks it to the shortest valid window ending at (or before) right before right moves again. Recording inside that loop catches every minimal window.
// Minimum Size Subarray Sum ≥ target  (positives only)
function minSubArrayLen(target: number, a: number[]): number {
  let left = 0, sum = 0, best = Infinity;
  for (let right = 0; right < a.length; right++) {
    sum += a[right];
    while (sum >= target) {                       // shrink WHILE valid
      best = Math.min(best, right - left + 1);    // record DURING
      sum -= a[left++];
    }
  }
  return best === Infinity ? 0 : best;
}

The one-line difference vs §4.2: longest shrinks while invalid and records after; shortest shrinks while valid and records during. Same skeleton, opposite trigger.

🎤 Interview lens Probed: when exactly do you record, and how do you report "no valid window"? · Escalation: min subarray sum → "Minimum Window Substring" (a need frequency map + a formed counter that tracks how many required chars are fully satisfied).

4.4 · Counting — "exactly K" via "at most K"

“You can't window ‘exactly’; window ‘at most’ twice and subtract.”

Why: "exactly K" isn't monotonic (a valid window can become invalid and valid again as you grow), so a single window can't count it. But "at most K" is monotonic. So: exactly(K) = atMost(K) − atMost(K−1).

🔑 Invariant — the counting trick In an atMost window [left, right] that's valid, every subarray ending at right and starting in [left, right] is also valid. That's right − left + 1 new subarrays — add it each step.
// Subarrays with exactly K distinct integers
function subarraysKDistinct(a: number[], k: number): number {
  const atMost = (k: number): number => {
    if (k < 0) return 0;
    const count = new Map<number, number>();
    let left = 0, res = 0;
    for (let right = 0; right < a.length; right++) {
      count.set(a[right], (count.get(a[right]) ?? 0) + 1);
      while (count.size > k) {
        const n = count.get(a[left])! - 1;
        if (n === 0) count.delete(a[left]); else count.set(a[left], n);
        left++;
      }
      res += right - left + 1;      // # of valid subarrays ending at right
    }
    return res;
  };
  return atMost(k) - atMost(k - 1);
}
🎤 Interview lens Probed: derive exactly = atMost(K) − atMost(K−1), and justify res += right−left+1. · Escalation: K distinct → "Binary Subarrays With Sum = goal" → "Count Number of Nice Subarrays" (exactly k odd numbers; same trick on parity).

4.5 · Monotonic deque — max/min in each window

“Keep a deque of candidates in decreasing order; the front is the answer.”

Setup: store indices in a deque whose values are strictly decreasing. The front is always the window max. Pop the back while it's ≤ the newcomer (it can never be the max again); pop the front when it slides out of the window.

🔑 Invariant — why it's safe The deque holds, in order, the indices that could still be the max of some future window — strictly decreasing by value, all inside [right−k+1, right]. A smaller-or-equal value behind a newer larger one is dominated forever, so dropping it loses nothing.
// Sliding Window Maximum — max of every size-k window
function maxSlidingWindow(a: number[], k: number): number[] {
  const dq: number[] = [];   // indices; a[dq] strictly decreasing
  const res: number[] = [];
  for (let i = 0; i < a.length; i++) {
    while (dq.length && a[dq[dq.length - 1]] <= a[i]) dq.pop();  // keep decreasing
    dq.push(i);
    if (dq[0] <= i - k) dq.shift();        // evict out-of-window front
    if (i >= k - 1) res.push(a[dq[0]]);    // front = current max
  }
  return res;
}
🎤 Interview lens Probed: prove amortized O(n) (each index pushed/popped once) and call out that JS Array.shift() is O(n) — use a head pointer for true O(n). · Escalation: max → min (mirror the comparison) → "Longest subarray with abs(max−min) ≤ limit" (run two deques at once).

The amortized argument right advances n times; left advances at most n times total across the whole run (never resets). So even though there's an inner while, the combined work is O(n) — say this explicitly, don't let the nested loop scare you into O(n²).

⚠️ 6 · Pitfalls — and the test that catches each

BugThe input that exposes it
Shrinking with if instead of while (longest) — one removal may not restore validity."aaab", k=1 distinct → an if leaves 2 distinct in the window.
Recording the answer at the wrong moment (longest = after; shortest = during).Min-window on [2,3,1,2,4,3], target 7 → recording after the shrink loop misses length 2 ([4,3]).
Off-by-one window length (right − left vs + 1).Any single-element answer, e.g. target = a[i] exactly → should report length 1.
Fixed window: forgetting to subtract the element that left.[1,1,1,1], k=2 → window sum keeps growing past 2 elements.
Using a naive window with negative numbers.[2,-1,2], target 3 → growing doesn't monotonically raise the sum; misses / mis-shrinks.
Deque stores values, not indices — can't evict by position.Any window where the max repeats, e.g. [5,3,5], k=2.
Frequency map keeps zero entries → size overcounts distinct.at-most-k on "aba", k=1 → stale a:0 inflates size.
🔗 This pattern, elsewhere Sliding window is a same-direction two-pointer — it's the Read/Write cousin from two-pointers.html with a shrink rule (and the converging vs. window distinction is sorting-vs-contiguity). Fixed windows are often replaceable by prefix sums. The monotonic deque is the monotonic-stack idea applied to a moving range — a stack open at both ends. Negative-number variant ("Shortest Subarray with Sum ≥ K") needs prefix sums + a monotonic deque — the bridge from this sheet to that one.
